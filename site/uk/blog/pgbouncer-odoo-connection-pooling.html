PgBouncer для Odoo: transaction pooling, який не ламає шину і queue_job

Навіщо багатьом воркерам Odoo пулер з'єднань, чому наївно налаштований transaction pooling ламає живі сповіщення Odoo та OCA queue_job, і робочий pgbouncer.ini з session pooling для бази postgres. А також розрахунок розмірів, моніторинг і пошук проблем.

Коли серверів Odoo кілька або воркерів сотні, кількість з'єднань з базою різко зростає: кожен процес Odoo тримає власний пул до db_maxconn з'єднань. PostgreSQL платить за кожне з'єднання окремим процесом і пам'яттю, і вже після кількох сотень активних з'єднань помітно сповільнюється. PgBouncer стоїть посередині: Odoo відкриває скільки завгодно дешевих клієнтських з'єднань, а PostgreSQL бачить лише невеликий пул.

Коротко: бази Odoo — у pool_mode = transaction, база postgres — у pool_mode = session (там шина Odoo виконує LISTEN imbus), а раннер OCA queue_job ходить напряму до PostgreSQL через jobrunner_db_host/port. Інакше чат, сповіщення й обробка завдань непомітно перестануть працювати.

Режими пулінгу і що потрібно Odoo

  • session: серверне з'єднання належить клієнту, доки той не від'єднається. Безпечно, але з довгими з'єднаннями Odoo майже нічого не заощаджує.
  • transaction: серверне з'єднання видається лише на час однієї транзакції. Саме тут виграш: сотні простоюючих з'єднань Odoo ділять кілька десятків справжніх.
  • statement: транзакцій з кількох запитів немає, тож для Odoo не підходить.
  • Звичайні запити Odoo працюють у режимі transaction: кожен запит — це одна транзакція, psycopg2 передає рівень ізоляції разом із BEGIN, а серверних prepared statements Odoo не використовує.

Дві пастки

  • Шина Odoo (живий чат, сповіщення, Discuss): процес gevent відкриває з'єднання з базою postgres і виконує LISTEN imbus (код: addons/bus/models/bus.py). LISTEN працює лише в сесії, тож у режимі transaction сповіщення губляться.
  • OCA queue_job: раннер виконує LISTEN queue_job і тримає advisory lock на рівні сесії (pg_try_advisory_lock), щоб працював лише один раннер. І те, і те потребує сесії, тому для раннера є окремі параметри з'єднання: jobrunner_db_host / jobrunner_db_port.

Налаштування

Розрахунок розмірів

default_pool_size≈ 2–4 × ядра CPU сервера БДстільки транзакцій одночасно працює в PostgreSQL

Приклад: 4 сервери Odoo по 33 воркери, сервер БД на 32 ядра. max_client_conn = 2000, default_pool_size = 64–100, max_db_connections = 150, у PostgreSQL max_connections = 200. Без PgBouncer PostgreSQL знадобилося б від кількох сотень до тисяч з'єднань.

Моніторинг

Найважливіша колонка в SHOW POOLS — cl_waiting: клієнти, які чекають на вільне серверне з'єднання. Якщо вона постійно більша за нуль, пул замалий або його займають довгі транзакції (довгі крони, звіти). maxwait показує, скільки чекає найстаріший клієнт.

Пошук проблем

  • Повідомлення чату й сповіщення з'являються лише після перезавантаження сторінки → база postgres працює в режимі transaction; задайте для неї pool_mode=session.
  • Завдання queue_job застрягають у стані «enqueued» → раннер підключається через transaction pooling; спрямуйте jobrunner_db_port на PostgreSQL або на запис із режимом session.
  • no more connections allowed (max_client_conn) → збільште max_client_conn і перевірте добуток процесів Odoo на db_maxconn.
  • query_wait_timeout → пул вичерпано: обережно збільште default_pool_size або знайдіть довгі транзакції (pg_stat_activity).
  • DROP DATABASE чи відновлення не вдається: database is being accessed → виконайте PAUSE mydb; або KILL mydb; у консолі PgBouncer чи працюйте напряму через порт 5432.
  • Менеджер баз Odoo не показує нову базу → перевірте, чи є запис із шаблоном *. Утім, з list_db = False це не має значення.

Коли він не потрібен

Один сервер Odoo з 10–20 воркерами поряд із PostgreSQL: з'єднань мало, і PgBouncer лише додає ще один компонент. Він виправданий, коли серверів Odoo кілька, воркерів багато, а max_connections сягає сотень. Наш калькулятор показує підказку, якщо значення перевищує 500.
