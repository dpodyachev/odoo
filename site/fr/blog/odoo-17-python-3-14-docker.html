Passer Odoo 17 à Python 3.14 – avec docker-compose

Une image odoo17-py314 maison, le code Odoo depuis Git monté dans site-packages, des tests sur la préproduction et un retour arrière en une minute.

Un Odoo 17 existant tourne dans Docker et doit passer à une version plus récente de Python, ici 3.14. Pourquoi : mises à jour de sécurité de l’image de base, bibliothèques plus récentes pour les modules spécifiques, et souvent un Python sensiblement plus rapide. Odoo 17 a été conçu pour Python 3.10–3.12 ; 3.14 n’est pas officiellement supporté – la règle est donc : d’abord la préproduction, ensuite la production.

L’idée : séparer l’image et le code Odoo

La nouvelle image odoo17-py314:latest ne contient que Python 3.14 et les dépendances. Le code Odoo vient d’un dépôt Git et est monté là où Python cherche ses paquets : ./extra_addons/odoo:/usr/local/lib/python3.14/site-packages/odoo. Les correctifs Odoo s’appliquent alors par git pull, sans reconstruire l’image.

Important : le chemin contient la version de Python. En passant de 3.12 à 3.14, remplacez aussi python3.12 → python3.14 dans le volume – sinon Python ne trouve pas le paquet odoo.

L’image

Le requirements.txt d’Odoo 17 fige des versions pour des Python plus anciens. Pour 3.14, on relève les versions des paquets avec extensions C (p. ex. gevent, greenlet, lxml, psycopg2, Pillow, reportlab) vers celles qui publient des wheels pour 3.14. wkhtmltopdf (rapports PDF) s’installe séparément, comme avant.

Déroulement

  • En préproduction, parcourir tous les processus clés : devis, factures, stock, rapports PDF, e-mails (dans un mail catcher), actions planifiées.
  • Surveiller dans le journal ImportError, DeprecationWarning et SyntaxWarning – les anciens modules avec des séquences d’échappement invalides dans les chaînes apparaissent en premier. Depuis Python 3.13, quelques anciens modules standard ont aussi disparu (PEP 594).
  • Une mise à jour des modules (-u) n’est pas nécessaire pour un simple changement de Python – le schéma de la base ne change pas.

Retour arrière

La base et le filestore restent intacts : un retour arrière dure le temps d’un redémarrage de conteneur.
