PgBouncer pour Odoo : le pooling par transaction sans casser le bus et queue_job

Pourquoi beaucoup de workers Odoo ont besoin d'un pooler de connexions, pourquoi le pooling par transaction casse les notifications en direct d'Odoo et OCA queue_job s'il est mis en place naïvement, et un pgbouncer.ini fonctionnel avec pooling de session pour la base postgres – plus dimensionnement, surveillance et dépannage.

Avec plusieurs serveurs Odoo ou des centaines de workers, le nombre de connexions à la base explose : chaque processus Odoo garde son propre pool de jusqu'à db_maxconn connexions. PostgreSQL paie chaque connexion avec un processus et de la RAM – et à partir de quelques centaines de connexions actives il ralentit nettement. PgBouncer se place entre les deux : Odoo ouvre autant de connexions client bon marché qu'il veut, PostgreSQL ne voit qu'un petit pool.

En bref : les bases Odoo en pool_mode = transaction, la base postgres en pool_mode = session (le bus Odoo y exécute LISTEN imbus), et le runner OCA queue_job directement vers PostgreSQL via jobrunner_db_host/port. Autrement, le chat, les notifications et le traitement des jobs cessent de fonctionner en silence.

Modes de pooling – et ce dont Odoo a besoin

  • session : une connexion serveur appartient au client jusqu'à sa déconnexion. Sûr, mais n'économise presque rien avec les connexions longues d'Odoo.
  • transaction : une connexion serveur seulement pendant une transaction. C'est là qu'est le gain : des centaines de connexions Odoo inactives se partagent quelques dizaines de vraies.
  • statement : pas de transactions à plusieurs instructions – inutilisable pour Odoo.
  • Les requêtes normales d'Odoo fonctionnent en mode transaction : chaque requête est une transaction, psycopg2 envoie le niveau d'isolation avec BEGIN, Odoo n'utilise pas de requêtes préparées côté serveur.

Les deux pièges

  • Bus Odoo (chat en direct, notifications, Discussion) : le processus gevent ouvre une connexion à la base postgres et exécute LISTEN imbus (source : addons/bus/models/bus.py). LISTEN ne fonctionne qu'en session – en mode transaction, les notifications se perdent.
  • OCA queue_job : le runner exécute LISTEN queue_job et garde un verrou consultatif de session (pg_try_advisory_lock) pour qu'un seul runner travaille. Les deux exigent une session – le runner reçoit ses propres paramètres de connexion : jobrunner_db_host / jobrunner_db_port.

Exemple : 4 serveurs Odoo × 33 workers, serveur BD à 32 cœurs. max_client_conn = 2000, default_pool_size = 64–100, max_db_connections = 150, PostgreSQL max_connections = 200. Sans PgBouncer, PostgreSQL aurait eu besoin de plusieurs centaines à milliers de connexions.

Surveillance

La colonne la plus importante est cl_waiting dans SHOW POOLS : les clients qui attendent une connexion serveur libre. Durablement au-dessus de zéro = pool trop petit ou longues transactions (crons longs, rapports) qui l'occupent. maxwait indique depuis combien de temps le plus ancien attend.

Dépannage

  • Les messages du chat et les notifications n'apparaissent qu'après rechargement → la base postgres est en mode transaction ; lui mettre pool_mode=session.
  • Les jobs queue_job restent en « enqueued » → le runner passe par le pooling par transaction ; mettre jobrunner_db_port vers PostgreSQL ou une entrée en session.
  • no more connections allowed (max_client_conn) → augmenter max_client_conn ; vérifier processus Odoo × db_maxconn.
  • query_wait_timeout → pool épuisé : augmenter prudemment default_pool_size ou trouver les longues transactions (pg_stat_activity).
  • DROP DATABASE / restauration échoue : database is being accessed → PAUSE mydb; ou KILL mydb; dans la console PgBouncer, ou travailler directement sur le port 5432.
  • Le gestionnaire de bases Odoo n'affiche pas une nouvelle base → entrée joker * présente ? Avec list_db = False, sans importance de toute façon.

Quand on n'en a pas besoin

Un serveur Odoo avec 10–20 workers à côté de PostgreSQL : le nombre de connexions est faible, PgBouncer n'ajoute qu'un composant. Il devient rentable avec plusieurs serveurs Odoo, beaucoup de workers, un max_connections dans les centaines élevées – notre calculateur affiche un avertissement au-delà de 500.
