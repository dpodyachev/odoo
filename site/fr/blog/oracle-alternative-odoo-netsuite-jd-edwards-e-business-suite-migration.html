Oracle alternative: moving from NetSuite, JD Edwards or E-Business Suite to Odoo

Cet article n’est pas encore disponible en français – voici la version anglaise.

Which Oracle ERP mid-size companies actually run, where the yearly costs come from, when Odoo is a good replacement and when staying on Oracle is the better choice – and how the data gets out of Oracle and into Odoo without duplicates.

“Oracle” in a mid-size company rarely means one product. It can be NetSuite in the cloud, a JD Edwards system that has been running for twenty years, an E-Business Suite installation with its own Oracle database, or a project on Fusion Cloud ERP. The question “should we move to Odoo?” has a different answer for each of them – so first: which Oracle do you have?

We are an independent Odoo service provider, not an Odoo partner and not an Oracle partner. Support dates and fees below are from Oracle's public statements as of November 2026; your own contract is what counts.

  • NetSuite has belonged to Oracle since 2016 and is sold as a subscription: the price depends on the modules switched on and the number of users.
  • JD Edwards EnterpriseOne 9.2 and E-Business Suite 12.2 are not being phased out: Oracle extends Premier Support every year and currently promises it until at least 2036. “Support is ending” is therefore rarely the real reason to move – cost and flexibility are.

Where the money goes

  • Annual support for on-premise licences: Oracle's standard rate is 22 % of the net licence fee, every year, and it is indexed. Licences that nobody uses any more are often still paid for.
  • Database licences: EBS and often JD Edwards run on an Oracle database, which is licensed separately – by processor or named user. Moving to new or virtual hardware can change what you owe.
  • Subscription (NetSuite, Fusion): yearly, by modules and users; extra modules or entities raise the price.
  • Specialists: JD Edwards CNC, EBS DBA, NetSuite SuiteScript – people with these skills are rare and expensive, and small companies often depend on one person.
  • Customisations: every change has to be re-tested at each update or upgrade – the same is true in Odoo, so count them honestly.

When Odoo is a good replacement

  • One to a few companies, up to a few hundred users, processes that are close to the standard: sales, purchase, inventory, manufacturing, accounting, projects, website and shop.
  • The Oracle system is used for 20 % of what it can do, but costs as if it were used fully.
  • You want your own server and database (Odoo Community or Enterprise on-premise) or a fixed price per user – without separate database licences: Odoo runs on PostgreSQL.
  • You want changes from developers you can find on the market: Odoo is Python and PostgreSQL.

When staying on Oracle is better

  • Dozens of legal entities with intercompany flows, several ledgers and consolidation that already works.
  • Strict regulation with validated systems (pharma, defence, utilities) – re-validation can cost more than any licence saving.
  • Deep industry functions you actually use (e.g. JD Edwards for engineering and construction projects, EBS process manufacturing).
  • A migration project now would collide with other big changes in the company. Then reduce Oracle costs first (unused licences, support level) and plan the move later.

Getting the data out

  • EBS and JD Edwards: you have the database – export with SQL into CSV files, one query per object. Take only active master data and open documents, not twenty years of history.
  • NetSuite: saved searches exported as CSV, or SuiteAnalytics. Plan for record limits and run large exports in parts.
  • Archive: keep the old system read-only for audits and look-ups, or export full history into a separate database. In Germany, accounting records must be kept for up to 10 years – the archive has to stay readable.

Loading with external IDs

The most useful trick: give every imported record an external ID made from the old Oracle number. Then each import can run again – after a fix in the CSV – and updates the same records instead of creating duplicates, and every Odoo record can be traced back to Oracle. Odoo's own import uses the load method; it can be called over the API:

  • load checks everything like the import screen: unknown country, invalid VAT number, missing required field – and returns the row and the reason.
  • One bad row rolls back the whole batch – so batches of a few hundred rows, and fix the data at the source.
  • Use a dedicated import user with an API key, not the admin password.

Rehearsal and cut-over

  1. Run the complete import on a copy of the Odoo database at least twice, with time measurement.
  2. Compare totals with Oracle: number of customers and items, stock value, open receivables and payables, trial balance.
  3. Fix the data in the export or the mapping – never by hand in Odoo, otherwise the next run loses the fix.
  4. Choose a quiet date (month end, ideally year end), freeze Oracle, run the final export and import, compare again.
  5. Keep Oracle read-only as the archive. A detailed cut-over plan is in our article on switching from an old ERP (link below).

Conclusion

Leaving Oracle is not about support ending – EBS and JD Edwards are supported for years to come. It is worth it when you pay for much more Oracle than you use, depend on rare specialists and want a system you can run yourself. Start with an inventory of what you really use and what it costs per year; then rehearse the migration on a copy until the totals match. If you want help with the technical part – export, mapping, import scripts, rehearsals – a small hour pack is enough for the first analysis.
