Cloudflare Access (Zero Trust) pas à pas – et quand c’est mieux qu’un mot de passe

Connexion par code e-mail ou SSO devant n’importe quel site ou système de test – sans une ligne de code. Mise en place en cinq étapes, comparaison avec Basic Auth via Pages Functions, pièges et pratique avec Odoo.

Ce site comporte deux pages de démonstration au contenu identique et à la protection différente : /test/ avec Basic Auth via Cloudflare Pages Functions (un mot de passe partagé, vérifié par une petite fonction) et /test2/ avec Cloudflare Access (connexion personnelle par code e-mail). Cet article explique Access et quand choisir l’un ou l’autre.

Qu’est-ce que Cloudflare Access ?

Access fait partie de Cloudflare Zero Trust. Il se place devant un site ou une application et ne laisse passer que les personnes connectées et autorisées par une règle. La connexion se fait par code à usage unique envoyé par e-mail, via Google, Microsoft, GitHub ou un SSO d’entreprise. L’offre gratuite permet jusqu’à 50 utilisateurs.

Règle simple : un mot de passe pour quelques personnes – Basic Auth. Personnes, rôles, journal, SSO – Access.

Mise en place en cinq étapes

  1. Activer Zero Trust. dash.cloudflare.com → Zero Trust → choisir un nom d’équipe (il devient <team>.cloudflareaccess.com) → offre Free. Cloudflare peut demander un moyen de paiement ; l’offre gratuite ne coûte rien.
  2. Méthode de connexion. Zero Trust → Settings → Authentication → Login methods → ajouter « One-time PIN ». En option Google, Microsoft ou GitHub.
  3. Créer l’application. Access → Applications → Add → Self-hosted. Saisir domaine et chemin, p. ex. 2027.pp.ua + test2. Choisir la durée de session (ici 24 h).
  4. Règle. Action « Allow », Include → « Emails » (adresses individuelles) ou « Emails ending in » (p. ex. @entreprise.fr). Sans règle correspondante, personne n’entre.
  5. Protéger tous les noms d’hôte. La même page est souvent accessible sous plusieurs noms : votre domaine, des domaines miroirs, projet.pages.dev. Ajoutez chacun comme destination supplémentaire de l’application.

C’est l’étape 5 qu’on oublie : pour la démo /test2/, la page n’était d’abord protégée que sur 2027.pp.ua – via goldberg.pp.ua et goldberg-odoo.pages.dev, elle aurait été ouverte. Vérifiez donc toujours tous les noms d’hôte.

Access devant Odoo

  • Placer entièrement les systèmes de préproduction et de test derrière Access – clients et testeurs se connectent avec leur e-mail, sans exposer de comptes Odoo supplémentaires.
  • Gestionnaire de bases (/web/database/*) en production : une application Access dédiée à ce seul chemin, réservée aux administrateurs.
  • API, webhooks, application mobile ne peuvent pas se connecter de façon interactive : utiliser une règle « Bypass » ou un service token pour ces chemins.
  • Important : Access ne protège que le passage par Cloudflare. Si le serveur Odoo est joignable directement par son IP, la protection est contournée – n’ouvrir le pare-feu qu’aux IP de Cloudflare ou utiliser Cloudflare Tunnel, et vérifier l’en-tête Cf-Access-Jwt-Assertion.
