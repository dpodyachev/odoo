Cloudflare Access (Zero Trust) step by step – and when it beats a password

Login with an e-mail code or SSO in front of any website or test system – without a line of code. Setup in five steps, comparison with Basic Auth via Pages Functions, pitfalls and Odoo practice.

This website has two demo pages with the same content and different protection: /test/ with Basic Auth via Cloudflare Pages Functions (one shared password, checked by a small function) and /test2/ with Cloudflare Access (personal login with an e-mail code). This article explains Access and when to use which.

What is Cloudflare Access?

Access is part of Cloudflare Zero Trust. It sits in front of a website or application and only lets through people who have signed in and are allowed by a policy. Sign-in works with a one-time code sent to the e-mail address, with Google, Microsoft, GitHub or company SSO. The free plan allows up to 50 users.

Rule of thumb: one password for a handful of people – Basic Auth. People, roles, audit log, SSO – Access.

Setup in five steps

  1. Enable Zero Trust. dash.cloudflare.com → Zero Trust → choose a team name (it becomes <team>.cloudflareaccess.com) → Free plan. Cloudflare may ask for a payment method; the free plan costs nothing.
  2. Login method. Zero Trust → Settings → Authentication → Login methods → add "One-time PIN". Optionally Google, Microsoft or GitHub.
  3. Create the application. Access → Applications → Add → Self-hosted. Enter domain and path, e.g. 2027.pp.ua + test2. Choose a session duration (24 h here).
  4. Policy. Action "Allow", Include → "Emails" (single addresses) or "Emails ending in" (e.g. @company.com). Without a matching policy nobody gets in.
  5. Protect every hostname. The same page is often reachable under several names: your own domain, mirror domains, project.pages.dev. Add each of them as another destination of the application.

Step 5 is the one people forget: for the /test2/ demo the page was first protected only on 2027.pp.ua – through goldberg.pp.ua and goldberg-odoo.pages.dev it would have been open. So always check every hostname.

Access in front of Odoo

  • Put stage and test systems completely behind Access – clients and testers sign in with their e-mail, without exposing extra Odoo accounts.
  • Database manager (/web/database/*) in production: a separate Access application for just that path, admins only.
  • API, webhooks, the mobile app cannot do an interactive login: use a "Bypass" policy or a service token for those paths.
  • Important: Access only protects the way through Cloudflare. If the Odoo server is reachable directly by IP, the protection is bypassed – open the firewall to Cloudflare IPs only, or use Cloudflare Tunnel, and verify the Cf-Access-Jwt-Assertion header.
