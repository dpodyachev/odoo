pg_dump and pg_restore for Odoo: every variant – Docker, systemd, remote server, filestore

How to back up and restore an Odoo database whether PostgreSQL runs in Docker, as a system service or on another server: formats, parallel jobs, single tables, the filestore, the ZIP from the database manager, a nightly script with rotation and the typical error messages.

“Make a backup” sounds like one command. In practice the command depends on where PostgreSQL runs: in a Docker container, as a normal system service (systemd) or on a separate or cloud database server. Each variant has its own pitfalls – a missing -T, the wrong client version, peer authentication, a folder the postgres user may not write to. Here are all variants side by side, with commands you can copy.

Short version: pg_dump -Fc (custom format) is the right default. Back up the filestore as well – without it Odoo has no attachments. Restore into a new database and swap names, check the restore log for ERROR, and test a restore regularly.

Step 0: find out how PostgreSQL runs

Important: db_host in odoo.conf tells you where Odoo connects. localhost inside a container means the container itself, db is usually the compose service name, an IP address means another server.

PostgreSQL as a system service (systemd, no Docker)

  • Local socket = peer authentication: PostgreSQL checks the Linux user name. That is why sudo -u postgres works without a password and pg_dump -U odoo as root does not.
  • > instead of -f with sudo -u postgres: the redirection is opened by your shell (root), so any target folder works.
  • Several clusters on one machine (an old 14 and a new 16): pg_lsclusters shows them, --cluster 16/main chooses the right one including the right binaries.

PostgreSQL in Docker

  • -T with docker compose exec (or -i without -t with docker exec) – otherwise the dump is silently corrupted and only fails on restore.
  • The official Odoo image contains a PostgreSQL client too – but often an older one than the server. If pg_dump complains about a version mismatch, run it in the database container or in a throw-away postgres:NN container of the server's version.
  • Do not dump the volume files (/var/lib/postgresql/data) of a running database – that is not a consistent backup.

Database on another server or managed (RDS, DigitalOcean, Hetzner …)

The version rule applies here too: the pg_dump client must be at least the server version. On an old workstation the client is often older – a postgres:NN container solves that without installing anything.

pg_dump does not stop Odoo: it reads a consistent snapshot while users keep working. It does block schema changes – a module update (-u) waits until the dump is done. On large databases a long dump also delays vacuum, so run it at night.

Restore

  • -T template0 -E UTF8: a clean database with the right encoding; the default template may contain extras.
  • --no-owner --role=odoo: the objects belong to the Odoo user even if the source server used a different role name.
  • -j 4 (number of CPU cores): speeds up restoring indexes considerably – only with a file, not with stdin.
  • A restored copy of production sends e-mails and runs cron jobs – before starting Odoo on it, neutralise it (see the article on stage restores).

Single tables, table of contents, exclusions

Restoring one table directly into production almost never works cleanly in Odoo: foreign keys, sequences and dependent tables do not match. Safer: restore into a scratch database, compare, then copy exactly the rows you need with SQL.

Odoo: the filestore belongs to the backup

A database without its filestore opens, but every attachment, product image and stored PDF is missing (“file not found” in the log). Database and filestore should come from the same point in time – dump first, then the filestore, both in the same script.

Nightly backup with check and rotation

  • set -euo pipefail: if pg_dump fails, the script stops and the || mail in crontab reports it.
  • pg_restore -l is a quick check that the file is a readable dump – not that the data restores cleanly. For that: a regular test restore on stage.
  • Keep copies off the server as well (rsync, R2/S3) – a backup on the same disk does not survive a disk failure or a deleted VPS.
