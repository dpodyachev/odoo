PgBouncer for Odoo: transaction pooling without breaking the bus and queue_job

Why many Odoo workers need a connection pooler, why transaction pooling breaks Odoo's live notifications and OCA queue_job if you do it naively, and a working pgbouncer.ini with session pooling for the database postgres – plus sizing, monitoring and troubleshooting.

With several Odoo servers or hundreds of workers the number of database connections explodes: every Odoo process keeps its own pool of up to db_maxconn connections. PostgreSQL pays for every connection with a process and RAM – and around a few hundred active connections it slows down noticeably. PgBouncer sits in between: Odoo opens as many cheap client connections as it likes, PostgreSQL only sees a small pool.

Short version: Odoo's databases in pool_mode = transaction, the database postgres in pool_mode = session (the Odoo bus runs LISTEN imbus there), and the OCA queue_job runner directly to PostgreSQL via jobrunner_db_host/port. Do it differently and chat, notifications and job processing silently stop working.

Pooling modes – and what Odoo needs

  • session: a server connection belongs to the client until it disconnects. Safe, but saves almost nothing with Odoo's long-lived connections.
  • transaction: a server connection only for the duration of one transaction. This is where the gain is: hundreds of idle Odoo connections share a few dozen real ones.
  • statement: no multi-statement transactions – unusable for Odoo.
  • Odoo's normal requests work in transaction mode: every request is a transaction, psycopg2 sends the isolation level with BEGIN, Odoo uses no server-side prepared statements.

The two traps

  • Odoo bus (live chat, notifications, Discuss): the gevent process opens a connection to the database postgres and runs LISTEN imbus (source: addons/bus/models/bus.py). LISTEN only works in a session – in transaction mode the notifications get lost.
  • OCA queue_job: the job runner runs LISTEN queue_job and holds a session advisory lock (pg_try_advisory_lock) so that only one runner works. Both need a session – the runner gets its own connection settings: jobrunner_db_host / jobrunner_db_port.

Example: 4 Odoo servers × 33 workers, DB server with 32 cores. max_client_conn = 2000, default_pool_size = 64–100, max_db_connections = 150, PostgreSQL max_connections = 200. Without PgBouncer, PostgreSQL would have needed several hundred to thousands of connections.

Monitoring

The most important column is cl_waiting in SHOW POOLS: clients waiting for a free server connection. Permanently above zero = pool too small or long transactions (long crons, reports) occupy it. maxwait shows how long the oldest waits.

Troubleshooting

  • Chat messages and notifications only appear after reload → the database postgres runs in transaction mode; set pool_mode=session for it.
  • queue_job jobs stay in “enqueued” → the runner connects via transaction pooling; set jobrunner_db_port to PostgreSQL or a session entry.
  • no more connections allowed (max_client_conn) → raise max_client_conn; check Odoo processes × db_maxconn.
  • query_wait_timeout → pool exhausted: raise default_pool_size carefully or find the long transactions (pg_stat_activity).
  • DROP DATABASE / restore fails: database is being accessed → PAUSE mydb; or KILL mydb; in the PgBouncer console, or work directly on port 5432.
  • Odoo database manager does not list a new database → wildcard entry * present? With list_db = False irrelevant anyway.

When you do not need it

One Odoo server with 10–20 workers next to PostgreSQL: the number of connections is small, PgBouncer only adds a component. It pays off with several Odoo servers, many workers, max_connections in the high hundreds – our calculator shows a hint above 500.
