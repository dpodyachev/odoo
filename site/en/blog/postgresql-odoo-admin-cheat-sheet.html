PostgreSQL for Odoo admins: the cheat sheet – backup, restore, users, queries, vacuum, indexes, tuning

Everything you need day to day: pg_dump/pg_restore/pg_basebackup and backups through Odoo with curl, sizes and the top 10 tables, users and rights, resetting passwords, finding and killing long queries, vacuum, EXPLAIN ANALYZE, indexes, and how PostgreSQL settings depend on Odoo's workers – plus pgtune, pgconfig.org and our calculator.

A page to bookmark: the PostgreSQL commands I use for Odoo, sorted by task. Odoo 16–19, PostgreSQL 13–17; replace mydb, odoo and hosts with yours.

Before anything that changes data – restore, DROP, VACUUM FULL, terminating sessions – make a fresh backup and try it on stage first.

1. Connecting and looking around in psql

2. How big are databases and tables?

In Odoo the top 10 is almost always mail_message, mail_tracking_value, ir_attachment (only metadata – the files are in the filestore), account_move_line, stock_move and the bus_bus/queue_job tables.

3. Backup: pg_dump, pg_dumpall, pg_basebackup

  • pg_dump – one database, logical, portable between versions. The standard for Odoo.
  • pg_dumpall --globals-only – roles and passwords, which pg_dump does not include.
  • pg_basebackup – the whole server, physical: basis for replicas and point-in-time recovery, only for the same major version.
  • --no-owner --no-acl (-O -x): no ALTER OWNER and GRANT in the dump – restorable under any role. Works for pg_dump as well as pg_restore.
  • There is no pg_backup tool – what is meant is usually one of these three.

5. Through Odoo: web and curl

Practical for small databases and for people without server access. For large ones (tens of GB) the zip export takes long and can hit limit_time_real – then use pg_dump. Never leave the database manager publicly reachable: list_db = False on production, enable it only temporarily or protect /web/database/* in nginx.

6. Users, databases and rights

Odoo's role should own its databases and have CREATEDB only if the database manager is used – never superuser.

7. Resetting passwords

Do not write an Odoo password directly into res_users.password with SQL: Odoo stores a hash and would not accept a plain value. Via odoo shell Odoo hashes it itself.

8. What is running right now – and stopping long queries

  • First pg_cancel_backend (cancels the query, the session stays), only then pg_terminate_backend.
  • idle in transaction for minutes is a bug in a script or an open shell – it holds locks and blocks vacuum.
  • Killing an Odoo worker's query rolls back its transaction – the user sees an error, data stays consistent.

9. Monitoring and vacuum

  • Autovacuum does the daily work – do not switch it off; tune it per table for the big Odoo tables.
  • VACUUM (ANALYZE) – online, frees space for reuse and refreshes statistics. After a restore or big import: ANALYZE.
  • VACUUM FULL – returns disk space to the OS but locks the table completely; maintenance window or pg_repack.
  • Watch: dead rows, last_autovacuum, transaction ID age, disk space, long transactions.

10. Slow queries: EXPLAIN ANALYZE

Where do the slow queries come from? log_min_duration_statement = 2000 writes every query over 2 s into the PostgreSQL log with its text; pg_stat_statements sums them up. Copy the query, run EXPLAIN (ANALYZE, BUFFERS) on a stage copy, read the plan from the most expensive node.

11. Indexes: which column has which index

In Odoo, add indexes preferably in the module (index=True on the field) – an index created by hand in SQL is unknown to Odoo. Before creating one, check that it is really used (EXPLAIN), and remove indexes that are never used.

12. PostgreSQL settings and Odoo workers

PostgreSQL and Odoo share the same budget: connections and – on one server – the same RAM. Odoo's settings therefore determine PostgreSQL's:

SettingRule of thumbDepends on Odoo
max_connectionsOdoo processes × ~3 + reserve, often 100–200workers + max_cron_threads + gevent; db_maxconn is a per-process cap, not the real usage; ×2 with a read replica (Odoo 18+)
shared_buffers25 % of the RAM PostgreSQL getson a shared server only of PostgreSQL's share – Odoo workers need their RAM too
effective_cache_size~75 % of that RAMonly a planner hint, allocates nothing
work_mem(RAM − shared_buffers) / (connections × 3)per sort/hash and connection – big Odoo reports use several at once; too high + many workers = OOM
maintenance_work_memRAM/16, max 2 GBfaster VACUUM, CREATE INDEX, module updates that build indexes
max_wal_size4 GB+ (more for big imports)mass imports, -u all and migrations write lots of WAL
random_page_cost1.1 on SSD/NVMemakes the planner use Odoo's indexes
jitoffOdoo runs many short queries
idle_in_transaction_session_timeoute.g. 30 minends forgotten transactions (shell sessions, broken scripts)

Odoo side: about 6 concurrent users per worker, at most 2 × CPU cores + 1 workers; per worker on average ~150 MB for light and ~1 GB for heavy requests (Odoo documentation). limit_memory_soft/hard are ceilings for peaks, not averages.

13. pgtune and pgconfig.org

  • PGTune (pgtune.leopard.in.ua): enter PostgreSQL version, OS, DB type, RAM, CPU, number of connections and storage – you get a postgresql.conf block. For Odoo choose “Web application” or “OLTP”.
  • PGConfig (pgconfig.org): similar, with profiles (web, OLTP, data warehouse, mixed, desktop), also outputs ALTER SYSTEM commands and explains each parameter.
  • Both know nothing about Odoo: they take “connections” as a given and assume the whole RAM belongs to PostgreSQL. With Odoo on the same server you must enter only PostgreSQL's share – and derive the connections from the workers.
