The customer's checklist explained: how to check each point – step by step for beginners

"You have owner rights in the repository" – but where do you see that on GitHub, GitLab or Bitbucket? Fourteen checks from our contractor checklist explained for people without IT background: what each one means, where to click, what it looks like, good signs and warning signs, with links to the official documentation.

In our article on automating Odoo operations we listed fourteen things a customer should demand from the contractor – and how to check them. "How to check" is easy to write and hard to do when you have never seen a Git repository or a backup report. This guide goes through each point the way you would explain it to a new colleague: what it means, where to look, what you should see.

The pictures are simplified schematic screens, not screenshots: menu names follow GitHub, Odoo and common tools, but they can differ slightly depending on version and language. Where several products are common (GitHub, GitLab, Bitbucket), the steps name all of them.

1. The repository belongs to you

All code, configuration and scripts of your Odoo live in a Git repository – a folder with complete history on a platform such as GitHub, GitLab or Bitbucket. Whoever is owner decides who has access and can take the code along. That must be your company, not the contractor or one of their employees.

  1. Ask the contractor for the repository link. The part after the platform name is the owner: github.com/your-company/odoo belongs to the organization *your-company*, github.com/max-dev/odoo to the personal account of *max-dev*.
  2. GitHub: open the repository ‣ *Settings* ‣ *Collaborators and teams*. In an organization repository you see roles (Read, Triage, Write, Maintain, Admin); the organization owners are under the organization ‣ *People* ‣ filter *Owner*. A repository of a personal account has only one owner – that account.
  3. GitLab: project ‣ *Manage* ‣ *Members* – roles from Guest to Owner; the project should be in a group that belongs to you.
  4. Bitbucket: repositories belong to a workspace; check *Workspace settings* ‣ users and groups (you as administrator) and *Repository settings* ‣ *Repository permissions*.
  5. Also possible: Azure DevOps or a self-hosted Gitea/GitLab – the question stays the same: who is administrator?
  6. Then let a deployment be done while you watch: the version on the server must come from this repository (same commit number in the pipeline and on the server).
  • Good: an organization or workspace in your company's name; you are Owner/Administrator; the contractor has Write or Maintainer.
  • Warning sign: the repository sits in the contractor's or an employee's personal account; you have no access at all; "we deploy from our laptop". Fix: let the repository be transferred to your organization (GitHub: *Settings* ‣ *Transfer ownership*).

2. The server can be rebuilt from the repository

"Server as code" means: the server is not set up by hand but by files in the repository – e.g. docker-compose.yml for Odoo and PostgreSQL, Ansible or Terraform for the server itself. Then anyone can build an identical server, and a total failure is a question of an hour.

  1. Look into the repository: are there files like docker-compose.yml, an ansible/ or terraform/ folder, a README.md with "how to build a server"?
  2. Ask the contractor to build a fresh staging server from the repository – on a new, empty machine.
  3. Measure the time from the empty machine to the login page of Odoo, and write it down: this is your recovery time in an emergency.
  4. Check that the new server has the same Odoo version and modules as production (Settings ‣ About / Apps).
  • Good: a fresh server in less than a day, without "I still have to remember…".
  • Warning sign: "that only works on the existing server", hand-written notes, manual steps not in the repository.

3. Backups in a second location – and a restore test

A backup is a copy of the database and of the attachments (filestore). Second location means another data centre or provider – a backup on the same server burns with it. Only a restore test proves the copy is usable.

  1. Ask where the backups are stored and how many days are kept. Expect: daily, at least 14–30 days, outside the server.
  2. Ask for the reports of the last restore tests – e-mails or chat messages with date, size, duration and a figure from the data (number of invoices, newest entry).
  3. Name a random date of the last weeks and ask for that backup to be restored on staging.
  4. Log in to that staging and look at the newest document of that day – does it match your memory?
  • Good: reports every day or week; a restore of any date within an hour or two; the restore time is known.
  • Warning sign: "backups are made" without proof; the only copy on the same server; nobody knows how long a restore takes.

4. Monitoring with alarms – and you see them

Monitoring is a program that checks the system every few minutes and raises an alarm: Odoo does not answer, the disk is full, the certificate expires, e-mails are stuck. The alarms go to a chat or e-mail – and you should be in it.

  1. Ask to be added to the alarm chat (Telegram, Teams, Slack) or the alarm e-mail list.
  2. Ask for the list of last month's alarms and what was done about each.
  3. Check that typical things are monitored: Odoo reachable, disk space, certificate, mail queue, failed scheduled jobs, age of the last backup.
  4. Tools you may hear about: Uptime Kuma, Healthchecks.io, Zabbix, Grafana, own bots – the tool matters less than whether someone reacts.
  • Good: warnings days before a problem (disk, certificate); each alarm has a short answer "cause – fixed".
  • Warning sign: you learn about outages from your employees; nobody can show an alarm of the last month.

More: Uptime Kuma ↗ · Healthchecks.io (cron jobs) ↗

5. A neutralised staging copy before every update

Staging is a copy of your Odoo for testing. Neutralised means: it cannot send e-mails to customers, scheduled jobs (reminders, subscriptions) and payments are off, and a coloured banner shows that it is a test system. Updates are tried there first.

  1. Ask for the staging address and log in. You should see a banner (red stripe or "TEST") at the top.
  2. Create a test document there and send it by e-mail to yourself. It must not arrive – it should land in the outgoing mail list with an error, or in a mail catcher such as Mailpit.
  3. Check in staging: Settings ‣ Technical ‣ *Scheduled Actions* – mostly inactive; *Outgoing Mail Servers* – none active.
  4. Ask when staging was last refreshed from production and which update was tested on it.
  • Good: your test e-mail does not arrive; staging is not older than the last update.
  • Warning sign: the test e-mail arrives (customers would get reminders from staging); "we test directly on production".

More: Odoo 18: neutralized database ↗ · Mailpit (mail catcher) ↗

6. Tests and CI for own modules

CI (continuous integration) is a robot that checks every change automatically before it is merged: installs the module, runs tests of important flows, checks the code style. On GitHub it shows as green ticks or red crosses next to each change.

  1. GitHub: repository ‣ *Actions* (list of runs) and ‣ *Pull requests* ‣ a request ‣ *Checks*. GitLab: *Build* ‣ *Pipelines*. Bitbucket: *Pipelines*.
  2. Look at the last ten changes: are they green? Who merged red ones?
  3. Check that merging is blocked without green checks (GitHub: *Settings* ‣ *Branches* / *Rules* – required status checks).
  4. Ask which business flows are tested – e.g. quote → invoice, stock move, DATEV export – and whether the tests also run on the next Odoo version.
  • Good: every change has checks; tests for your critical flows; merging only when green.
  • Warning sign: no Actions/Pipelines at all; regularly red builds that get merged anyway.

7. As little own code as possible

Every own module costs money twice: when it is written and at every version upgrade. Often the standard, Odoo Studio or a free community module (OCA) can do the same. A good contractor can justify every own module.

  1. Ask for a list of own modules with one sentence each: why it exists, and why the standard or OCA is not enough.
  2. Ask for the size in lines of code (e.g. counted with the tool *cloc*) – it shows where the upgrade costs will be.
  3. For each module, search yourself briefly: Odoo Apps store and OCA on GitHub – is there something ready-made?
  4. Question modules that only add a field or rename labels – Studio or settings may do that.
  • Good: few modules, each with a clear reason; bug fixes are also sent to OCA/Odoo (then they disappear later).
  • Warning sign: dozens of modules nobody can explain; copies of whole standard modules.

More: OCA on GitHub ↗ · Odoo Apps store ↗ · cloc (count lines of code) ↗

8. An upgrade plan to the next version

Odoo releases a new version every year and supports only the last three. Sooner or later every installation has to move. An upgrade plan says when, what will break and what it costs – based on a test upgrade of a copy, not on guesswork.

  1. Ask which Odoo version you run and until when it is supported (Odoo's "supported versions" page).
  2. Ask for a test upgrade of a copy of production to the next version: Enterprise via Odoo's upgrade service, Community via OpenUpgrade.
  3. Read the report: duration, which own modules work, which must be adapted and how long that takes.
  4. Get an offer based on this report, with a date – and a test phase on staging before the real switch.
  • Good: a written plan with dates and costs, based on a real test run.
  • Warning sign: "we will see when it is time"; the version is already out of support.

More: Odoo: supported versions ↗ · Odoo: upgrade ↗ · OpenUpgrade (OCA) ↗

9. Fixed scope with acceptance criteria

Instead of "we work and bill the hours", every item of the project is described with a test case – what must work, so that you can accept it. A common format is *Given – When – Then*.

  1. Ask for the list of items with a test case each, before the work starts.
  2. Check that the test cases are in your language and testable without IT knowledge ("Given … When … Then …").
  3. Accept item by item: do the test yourself on staging, then sign off (e-mail or tick in the project plan).
  4. Changes of scope: new item with its own test case and price – not hidden in "additional hours".
  • Good: you know what you pay for, and when an item is finished.
  • Warning sign: only an hour budget; "done" without anything you could test.

More: Given – When – Then ↗

10. Documentation and handover

The admin guide answers the questions of an emergency: what runs where, how to restore, who has which access, whom to call. It belongs in the repository (e.g. README.md), so it stays with you.

  1. Open the repository and look for README.md or a docs/ folder: are there sections on servers, backups and restore, access, contacts?
  2. The real test: ask a third person (an IT-savvy colleague or another service provider) to restore a backup on a test machine using only this guide.
  3. Write down where they got stuck – each point is a gap in the documentation.
  4. Repeat once a year or after big changes.
  • Good: the third person manages it without calling the contractor.
  • Warning sign: "it is all in my head"; documentation outside your reach (contractor's wiki).

11. Personal accounts with 2FA – no secrets in the repository

Everybody has their own account – in Odoo, on the server, on GitHub – protected with two-factor authentication (2FA: password plus code from the phone). Passwords and keys (secrets) are kept in a password manager or secret store, never in the code.

  1. GitHub organization: *People* shows the members and whether 2FA is on; *Settings* ‣ *Authentication security* can require 2FA for everyone. GitLab: group settings ‣ require 2FA.
  2. Ask for the list of all accounts (Odoo admins, server, Git, hosting, DNS) and who uses each one. Shared accounts like "admin" for several people: warning sign.
  3. Remove people who left – they appear in the lists above.
  4. Let the repository be scanned for secrets (GitHub *secret scanning* or the tool *gitleaks*) and ask for the result.
  5. In Odoo: users with administrator rights should use 2FA (user preferences ‣ *Account Security*).
  • Good: every account belongs to one person; 2FA everywhere; the scan finds no secrets.
  • Warning sign: one admin password for all; passwords in e-mails or in the repository; former employees still have access.

12. Training material in your language

Short videos and texts of your processes (not general Odoo videos) in the language of your employees, plus checklists for typical problems. A new employee should be able to do the everyday tasks with them.

  1. Ask for the list of material: which processes, which language, where it is stored (it should be with you).
  2. Test: give a new employee one typical task (e.g. create an invoice from a delivery) and only the material – no help.
  3. Note where they got stuck; the contractor adds a video or a sentence.
  4. Check that the material is updated after changes and upgrades.
  • Good: the task is done with the material alone; videos of 2–5 minutes with a transcript.
  • Warning sign: only links to general Odoo videos; material in a language your team does not use.

13. Reaction times and a monthly report

A short monthly report shows the hours by category: support (something does not work), administration (updates, backups), development (new functions). If the contractor automates, support and administration must go down over time – the report makes that visible.

  1. Agree on reaction times in the contract (e.g. 4 working hours for "Odoo is down", 2 days for questions).
  2. Ask for a monthly report with hours per category and the list of tickets.
  3. Every quarter: compare the categories. Falling support and admin hours = automation works; rising = ask why.
  4. Check a few tickets: was the reaction time kept?
  • Good: the same categories every month; trends you can see.
  • Warning sign: one lump sum "IT services" without breakdown; support hours that grow every quarter.

14. Exit clause and trial export

At the end of the contract you must get everything needed to continue with someone else: the database, the attachments (filestore), the repository and the guide. The contract says so – and a trial export shows it works.

  1. Put it in the contract: export of database, filestore and repository within a few days, in standard formats, without extra cost.
  2. Do a trial export once: ask for the files (or download a backup yourself – on Odoo Online in the database manager).
  3. Give the export to a third person or another service provider: can they start Odoo with it on a test machine?
  4. Check the result: are the newest documents there, and the attachments (PDFs, images)?
  • Good: Odoo runs elsewhere with your data within a day.
  • Warning sign: "the export costs extra"; data only in formats of the contractor; attachments missing.

More: Odoo Online: database management (download a backup) ↗ · PostgreSQL: SQL dump ↗

Conclusion

None of these checks needs IT knowledge – only a link, a question and the willingness to look. Do the first round with the contractor, write down the results and repeat the most important checks (backup restore, alarm chat, trial export) once a year. A good contractor will welcome this, because it shows that the work is done properly. We work this way with customers in Germany, Austria and Switzerland and show each point on request.
