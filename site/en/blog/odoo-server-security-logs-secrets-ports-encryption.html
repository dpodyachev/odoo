Odoo server security: secrets in logs, password rotation, closed ports and encrypted traffic between servers

What a real audit found – an integration token and phone numbers in the nginx access log – and the four things to check on every Odoo installation: secrets and personal data in URLs and logs, rotation of passwords and keys, ports that must not be public, and encryption of traffic between servers, including against your own admins.

During a routine check of a production Odoo installation with a call-centre integration, the nginx access log turned up something unpleasant: every request of the integration carried its access token in the URL (?auth=…), together with customer phone numbers. Thousands of lines a day, kept for days, readable by every administrator, copied into backups and monitoring. Nobody had done anything wrong on purpose – the integration simply sent its parameters as a GET query.

Short version: no secrets and no personal data in URLs; logs only with paths and a limited retention; rotate passwords and keys on a schedule and when people leave; only 80/443 public (Docker bypasses ufw!); encrypt traffic between Odoo, PostgreSQL, replica and integrations – a private network is not a secure network.

1. Secrets and personal data in URLs and logs

A query string is logged everywhere: nginx access logs, load balancers and CDNs, the browser history, Referer headers to third-party sites, APM and monitoring tools. Whoever can read one of these places has the token – and with it the integration. Phone numbers are personal data under the GDPR: storing them in logs for weeks without purpose is a compliance problem of its own.

  • Move tokens into a header (Authorization) and data into the POST body; then rotate the token – the old one is in the logs.
  • Log only $uri (path without query string) – or no access log at all for integration endpoints.
  • Limit retention: logrotate (14–30 days), Docker max-size/max-file; delete old logs containing secrets.
  • Logs readable only by root/adm; integration logs (pm2, node) often contain full requests with passwords – check them too.

2. Rotating passwords and keys

A secret that never changes is eventually known to everyone who ever had access: former employees, contractors, an old laptop, a chat history. Rotation limits how long a leak is useful.

  • Inventory first: a list of all secrets – PostgreSQL roles, admin_passwd, Odoo API keys, integration tokens, SMTP, payment/shipping/bank credentials, SSH keys, cloud tokens – with owner and date of the last change.
  • When: immediately when someone with access leaves or a leak is suspected; otherwise on a schedule (e.g. every 6–12 months for shared secrets).
  • How without downtime: create the new key, switch the consumer, then revoke the old one. For the Odoo database password a short restart is enough.
  • Where: not in git, not in chat; files chmod 600/640, a password manager or secret store for the team.

3. Ports: only 80 and 443 to the outside

The classic trap: the firewall (ufw) shows “deny”, yet Odoo is reachable on 8069 from the internet. Docker writes its own iptables rules for published ports and bypasses ufw. Publish only on 127.0.0.1 or not at all, and block in the DOCKER-USER chain – plus a provider firewall in front of the server.

4. Traffic between servers can be read

Odoo ↔ PostgreSQL, primary ↔ replica, Odoo ↔ integrations often run unencrypted “because it is the internal network”. But inside that network sit other virtual machines, the hosting provider's infrastructure – and administrators. Anyone with root on one of the hosts or access to the network path can record the traffic with tcpdump: customer data, invoices, session cookies, API tokens. That includes a dishonest or careless admin of your own.

If several services need protection at once, a WireGuard network between the servers is the simplest blanket: everything between the hosts is encrypted, services listen only on the tunnel address.

5. Against the insider: least privilege and traceability

  • Personal accounts instead of one shared user with passwordless sudo; SSH keys per person; remove leavers on all hosts the same day.
  • Secrets readable only by the service user (odoo.conf 640, .env 600) – config and log files with 644 and passwords are common.
  • Log root commands (auditd) and ship logs to a place the admin of the server cannot edit.
  • 2FA for the cloud console, the domain registrar, Cloudflare, GitHub – that is where the keys to everything are.
  • After a person leaves: rotate everything they could read, not only their login.

Checklist

  • No tokens/passwords/phone numbers in URLs; access logs without query strings; retention ≤ 30 days.
  • Inventory of secrets with owner and date; rotation on leaving and on schedule.
  • From outside only 80/443 (and SSH from known addresses); Docker ports on 127.0.0.1; DOCKER-USER rules; provider firewall.
  • PostgreSQL with ssl = on, hostssl and db_sslmode = verify-full; replication and integrations over TLS or WireGuard.
  • Personal admin accounts, auditd, 2FA on all consoles, secrets not world-readable.
