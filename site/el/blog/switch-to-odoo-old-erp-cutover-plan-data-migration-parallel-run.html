Switching to Odoo from an old ERP: cut-over plan, data migration and parallel run – without chaos

Το άρθρο δεν είναι ακόμη διαθέσιμο στα ελληνικά – ακολουθεί η αγγλική έκδοση.

How to move a running company – for example a manufacturer – from an old ERP or Excel to Odoo: list processes and interfaces, migrate only what you need, rehearse on a copy, choose big bang, phases or a parallel run, plan the cut-over weekend with checks, define when to roll back, and support the first week.

The risky part of an ERP switch is not Odoo. It is the moment when orders, stock and invoices stop living in the old system and start living in the new one – while production keeps running, trucks arrive and customers call. This article is the plan we use for that moment, from the technical side: what to list first, which data to move, how to rehearse, and how to decide on go-live day.

This is a technical checklist, not legal or tax advice. Questions about accounting periods and retention obligations belong with your tax advisor.

1. List processes and interfaces – before anything else

Write down what really happens today, not what the old manual says. For a manufacturer that is typically: quote → sales order → production order → material consumption → delivery → invoice → payment, plus purchasing and goods receipt. For each step note who does it, in which system, and what the result is.

  • Interfaces: web shop, EDI with large customers, shipping labels, bank files, DATEV, time recording, machine data, the Excel file that someone fills every Friday. Forgotten interfaces are the most common go-live surprise.
  • Reports people rely on: open orders, stock lists, monthly figures. If a report disappears, people go back to Excel.
  • Special cases: consignment stock, customer-supplied material, serial numbers, partial deliveries, credit notes.

2. Which data to migrate – and which not

Migrate what you need to keep working, not the complete history. History makes the migration slower, more expensive and full of old errors.

DataMigrate?Note
Customers, suppliers, contactsyesclean up duplicates first
Products, bills of materials, routingsyesonly active items
Open sales and purchase ordersyeswith remaining quantities
Open receivables and payablesyesas open items, one entry per invoice
Opening balances (trial balance)yeson the cut-over date, agreed with the tax advisor
Opening stockyesquantity and value per product and location
Closed orders, old invoices, old movementsnokeep the old system read-only or as an export archive

The old system is not switched off on go-live day. It stays available read-only – for questions about old orders and for the retention period.

3. Rehearse on a copy – at least twice

Every import runs first on a test copy of Odoo with scheduled jobs and outgoing mail switched off, so nobody receives a test invoice. We describe how to set up such a copy in a separate article. The first rehearsal finds the mapping errors, the second measures how long the import takes – that time goes into the cut-over plan.

After each rehearsal key users test their daily work on the copy: create an order, produce, deliver, invoice. Whatever they cannot do there, they will not be able to do on Monday.

4. Big bang, phases or parallel run?

ApproachProContraFits when
Big bang (all at once)one cut-over, no interfaces between old and newhigh risk on one daysmall and medium companies, few interfaces
In phases (e.g. CRM/sales first, then warehouse, then accounting)smaller steps, team learns graduallytemporary interfaces old ↔ new, longer projectmany locations or complex production
Parallel run (both systems for some weeks)results can be compareddouble entry, people get tired, data drifts apartonly for short periods and selected areas, e.g. payroll or a pilot

Our default recommendation for a single company is a well rehearsed big bang at a month start, with accounting following at the start of a period. A full parallel run sounds safe but rarely survives the second week.

5. The cut-over weekend

  1. Thursday: last rehearsal done, import times known, go/no-go meeting with key users.
  2. Friday noon – freeze: no new orders or bookings in the old system; deliveries already prepared are finished.
  3. Friday evening – final export: master data, open orders, open items, stock count or stock list. Write down the control numbers from the old system (number of customers, open amounts, stock value).
  4. Saturday – import in the same order as in the rehearsal, with a backup of the database before each big step.
  5. Saturday afternoon – reconciliation: record counts, stock value, open receivables and payables, trial balance against the old system. The script below does the counts and totals.
  6. Sunday – key-user test: one complete order from quote to invoice, printing, e-mail, interfaces.
  7. Sunday evening – go / no-go based on the rollback criteria.

6. Rollback criteria – decided in advance

Decide before the weekend, in writing, when you go back to the old system. Typical criteria: open amounts or stock value differ and the difference cannot be explained; invoices cannot be posted; a critical interface (shop, EDI, shipping) does not work and there is no manual workaround. Because the old system was only frozen, rolling back means unfreezing it – which is exactly why the freeze must be complete.

7. The first week (hypercare)

  • Key users and the technical team are available daily, questions are collected in one list.
  • A short meeting every morning: what is blocked, what is just unfamiliar.
  • Monitoring and backups run from the first day – not after the project.
  • Small fixes go to the test copy first, then to production.

8. Typical mistakes

  • Dirty data migrated: duplicate customers and dead products move into Odoo and stay there.
  • Too many customizations: rebuilding the old system in Odoo makes every update expensive. Change the process first, the code second.
  • No key-user training: people learn the new system on go-live day under pressure.
  • Interfaces forgotten: the weekly Excel or the label printer only shows up on Monday.
  • Accounting periods ignored: switching in the middle of a period or without agreement with the tax advisor; DATEV export not tested.

Conclusion

An ERP switch without chaos is mostly preparation: an honest list of processes and interfaces, a small migration scope, two rehearsals, a timed cut-over plan and rollback criteria decided in advance.
