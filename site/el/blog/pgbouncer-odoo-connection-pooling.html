PgBouncer για Odoo: transaction pooling χωρίς να σπάσει το bus και το queue_job

Γιατί πολλοί workers του Odoo χρειάζονται connection pooler, γιατί το transaction pooling σπάει τις ζωντανές ειδοποιήσεις του Odoo και το OCA queue_job αν στηθεί αφελώς, και ένα λειτουργικό pgbouncer.ini με session pooling για τη βάση postgres – μαζί με διαστασιολόγηση, παρακολούθηση και αντιμετώπιση προβλημάτων.

Με πολλούς servers Odoo ή εκατοντάδες workers ο αριθμός των συνδέσεων στη βάση εκρήγνυται: κάθε διεργασία Odoo κρατά δικό της pool έως db_maxconn συνδέσεις. Η PostgreSQL πληρώνει κάθε σύνδεση με μια διεργασία και RAM – και από μερικές εκατοντάδες ενεργές συνδέσεις και πάνω επιβραδύνεται αισθητά. Το PgBouncer μπαίνει ενδιάμεσα: το Odoo ανοίγει όσες φθηνές συνδέσεις πελάτη θέλει, η PostgreSQL βλέπει μόνο ένα μικρό pool.

Συνοπτικά: οι βάσεις του Odoo με pool_mode = transaction, η βάση postgres με pool_mode = session (εκεί το bus του Odoo εκτελεί LISTEN imbus), και ο runner του OCA queue_job απευθείας στην PostgreSQL μέσω jobrunner_db_host/port. Αλλιώς το chat, οι ειδοποιήσεις και η επεξεργασία των jobs σταματούν σιωπηλά.

Λειτουργίες pooling – και τι χρειάζεται το Odoo

  • session: μια σύνδεση server ανήκει στον πελάτη μέχρι να αποσυνδεθεί. Ασφαλές, αλλά δεν εξοικονομεί σχεδόν τίποτα με τις μακρόβιες συνδέσεις του Odoo.
  • transaction: μια σύνδεση server μόνο για τη διάρκεια μιας συναλλαγής. Εδώ είναι το κέρδος: εκατοντάδες αδρανείς συνδέσεις Odoo μοιράζονται λίγες δεκάδες πραγματικές.
  • statement: χωρίς συναλλαγές πολλών εντολών – άχρηστο για το Odoo.
  • Τα κανονικά αιτήματα του Odoo λειτουργούν σε transaction mode: κάθε αίτημα είναι μία συναλλαγή, το psycopg2 στέλνει το επίπεδο απομόνωσης με το BEGIN, το Odoo δεν χρησιμοποιεί prepared statements στον server.

Οι δύο παγίδες

  • Bus του Odoo (ζωντανό chat, ειδοποιήσεις, Discuss): η διεργασία gevent ανοίγει σύνδεση στη βάση postgres και εκτελεί LISTEN imbus (πηγή: addons/bus/models/bus.py). Το LISTEN λειτουργεί μόνο σε session – σε transaction mode οι ειδοποιήσεις χάνονται.
  • OCA queue_job: ο runner εκτελεί LISTEN queue_job και κρατά ένα session advisory lock (pg_try_advisory_lock) ώστε να δουλεύει μόνο ένας runner. Και τα δύο χρειάζονται session – ο runner παίρνει δικές του ρυθμίσεις σύνδεσης: jobrunner_db_host / jobrunner_db_port.

Διαστασιολόγηση

Παράδειγμα: 4 servers Odoo × 33 workers, server βάσης με 32 πυρήνες. max_client_conn = 2000, default_pool_size = 64–100, max_db_connections = 150, PostgreSQL max_connections = 200. Χωρίς PgBouncer η PostgreSQL θα χρειαζόταν μερικές εκατοντάδες έως χιλιάδες συνδέσεις.

Παρακολούθηση

Η σημαντικότερη στήλη είναι η cl_waiting στο SHOW POOLS: πελάτες που περιμένουν ελεύθερη σύνδεση server. Μόνιμα πάνω από μηδέν = πολύ μικρό pool ή μακριές συναλλαγές (μακριά cron, αναφορές) που το καταλαμβάνουν. Το maxwait δείχνει πόση ώρα περιμένει ο παλαιότερος.

Αντιμετώπιση προβλημάτων

  • Τα μηνύματα chat και οι ειδοποιήσεις εμφανίζονται μόνο μετά από ανανέωση → η βάση postgres τρέχει σε transaction mode· ορίστε της pool_mode=session.
  • Τα jobs του queue_job μένουν σε «enqueued» → ο runner συνδέεται μέσω transaction pooling· βάλτε το jobrunner_db_port στην PostgreSQL ή σε καταχώριση session.
  • no more connections allowed (max_client_conn) → αυξήστε το max_client_conn· ελέγξτε διεργασίες Odoo × db_maxconn.
  • query_wait_timeout → εξαντλημένο pool: αυξήστε προσεκτικά το default_pool_size ή βρείτε τις μακριές συναλλαγές (pg_stat_activity).
  • Αποτυγχάνει το DROP DATABASE / η επαναφορά: database is being accessed → PAUSE mydb; ή KILL mydb; στην κονσόλα του PgBouncer, ή δουλέψτε απευθείας στη θύρα 5432.
  • Ο database manager του Odoo δεν δείχνει νέα βάση → υπάρχει η καταχώριση μπαλαντέρ *; Με list_db = False δεν έχει σημασία ούτως ή άλλως.

Πότε δεν το χρειάζεστε

Ένας server Odoo με 10–20 workers δίπλα στην PostgreSQL: οι συνδέσεις είναι λίγες, το PgBouncer απλώς προσθέτει ένα ακόμα στοιχείο. Αξίζει με πολλούς servers Odoo, πολλούς workers, max_connections στις υψηλές εκατοντάδες – ο υπολογιστής μας δείχνει ειδοποίηση πάνω από 500.
