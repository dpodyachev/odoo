Odoo apps and modules: what you really need – and what each one costs you later

Το άρθρο δεν είναι ακόμη διαθέσιμο στα ελληνικά – ακολουθεί η αγγλική έκδοση.

Standard apps (Community or Enterprise), OCA modules, paid modules from the Odoo Apps Store and your own code: where each comes from, what licence it has, who fixes it, and why every extra module costs money again at every major upgrade. With a checklist for third-party modules and an SQL query that lists what is installed.

Installing a module in Odoo takes one click. Removing it a year later, once data and other modules depend on it, can take days. That asymmetry is the whole point of this article: the question is not only “does this module do what we need?”, but “who keeps it working for the next five versions?”.

We are an independent Odoo service provider, not an Odoo partner. Which apps belong to which edition changes between versions – check the edition comparison on odoo.com for your version before deciding.

Four places modules come from

  • Standard apps from Odoo S.A. – Sales, Purchase, Inventory, Manufacturing, CRM, Website and so on. Some exist in Community (free, LGPL-3), others only in Enterprise (subscription, Odoo Enterprise licence).
  • OCA modules – the Odoo Community Association maintains hundreds of repositories on GitHub (stock-logistics, account-financial-tools, server-tools, …). Free, mostly AGPL-3 or LGPL-3.
  • Odoo Apps Store – modules from many vendors, free or paid, often under the OPL-1 licence. Quality ranges from excellent to unusable.
  • Your own modules – code written for your company: a field, a report, an integration, a business rule.

Community or Enterprise: where the line runs

The core business flow – quotation, order, delivery, invoice, purchase, stock, manufacturing orders – works in Community. Enterprise adds apps and comfort around it. Typical Enterprise-only apps: Studio, Barcode, Quality, PLM, Helpdesk, Field Service, Planning, Sign, Knowledge, Documents. Accounting is the most common surprise: Community has the Invoicing app (invoices, payments, journals), but the full accounting app with bank reconciliation widgets, financial reports and many localisation reports is Enterprise.

This matters for module choice: if you run Community and need a function that only exists in Enterprise, you either buy Enterprise, find an OCA equivalent, buy an App Store module or build it. Each path has a different long-term price.

Every module is paid again at every upgrade

Odoo releases a major version every year, and each one changes the framework: field types, views, JavaScript (OWL), method signatures. A module written for 17.0 does not install in 18.0 without being ported. For Odoo's own apps that is Odoo's job. For everything else it is somebody's job – the OCA volunteers, the App Store author or your developer – and often it ends up being yours.

That is why we count third-party and own modules when estimating an upgrade. The number of modules, the number of overridden core methods and the amount of data they own decide the effort far more than the number of users.

Checklist: before you install a third-party module

  1. Is there a branch for your version – and the next one? On GitHub, look for the 17.0, 18.0 … branch. If the module stopped at an older version, you will be the one porting it.
  2. When was the last commit, and are issues answered? A repository without activity for two years is a warning sign.
  3. Are there tests? A tests/ folder and green CI on the OCA repository mean someone checks the module on every change.
  4. What does it depend on? Read depends in __manifest__.py. A small feature that pulls in five other modules brings five upgrade problems.
  5. Does it override core methods? Search the code for overrides of create, write, _action_confirm, _compute_* of standard models, and for JavaScript patches. The more it changes standard behaviour, the more likely it breaks with other modules and upgrades.
  6. Licence compatibility. AGPL-3 requires that you provide the source of changes when users access the software over a network – usually fine for internal use, important if you sell a product on top. OPL-1 allows use and modification but not redistribution, and each database needs its own purchase. Mixing AGPL and OPL code in one module of your own is a licensing question to clarify before writing it.
  7. Install on a copy first. Install on a test copy of your database, run the business flows, then uninstall and see what remains. Some modules leave fields and data behind.

Fewer modules

  • Configuration before code. Many requests are solved with standard settings: routes, sequences, access rights, automated actions, mail templates.
  • One own module instead of five small ones. A company module that collects small changes (a field here, a report there) is easier to port than five App Store modules from five authors.
  • Remove what nobody uses. Modules that were installed for a test and forgotten still have to be upgraded.
  • Prefer OCA over a paid single-author module when both exist – the OCA module usually gets ported because several companies need it.
  • Write down why each third-party module is there. A one-line reason per module saves hours at the next upgrade.

Conclusion

Choose modules the way you choose a supplier: by who will still deliver in three years. Standard apps first, then OCA, then a carefully checked App Store module, and your own code where the business really differs.
