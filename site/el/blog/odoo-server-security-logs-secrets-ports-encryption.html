Ασφάλεια server Odoo: μυστικά στα logs, εναλλαγή κωδικών, κλειστές θύρες και κρυπτογραφημένη κίνηση μεταξύ servers

Τι βρήκε ένας πραγματικός έλεγχος – ένα token διασύνδεσης και αριθμούς τηλεφώνου στο access log του nginx – και τα τέσσερα πράγματα που πρέπει να ελέγχετε σε κάθε εγκατάσταση Odoo: μυστικά και προσωπικά δεδομένα σε URL και logs, εναλλαγή κωδικών και κλειδιών, θύρες που δεν πρέπει να είναι δημόσιες, και κρυπτογράφηση της κίνησης μεταξύ servers, και απέναντι στους δικούς σας διαχειριστές.

Σε έναν έλεγχο ρουτίνας μιας εγκατάστασης Odoo παραγωγής με διασύνδεση τηλεφωνικού κέντρου, το access log του nginx αποκάλυψε κάτι δυσάρεστο: κάθε αίτημα της διασύνδεσης κουβαλούσε το token πρόσβασης στο URL (?auth=…), μαζί με αριθμούς τηλεφώνου πελατών. Χιλιάδες γραμμές την ημέρα, κρατημένες για μέρες, αναγνώσιμες από κάθε διαχειριστή, αντιγραμμένες σε αντίγραφα ασφαλείας και παρακολούθηση. Κανείς δεν έκανε σκόπιμα λάθος – η διασύνδεση απλώς έστελνε τις παραμέτρους της ως GET query.

Συνοπτικά: κανένα μυστικό και κανένα προσωπικό δεδομένο σε URL· logs μόνο με διαδρομές και περιορισμένη διάρκεια διατήρησης· εναλλαγή κωδικών και κλειδιών προγραμματισμένα και όταν φεύγουν άτομα· μόνο 80/443 δημόσια (το Docker παρακάμπτει το ufw!)· κρυπτογραφήστε την κίνηση μεταξύ Odoo, PostgreSQL, replica και διασυνδέσεων – ένα ιδιωτικό δίκτυο δεν είναι ασφαλές δίκτυο.

1. Μυστικά και προσωπικά δεδομένα σε URL και logs

Ένα query string καταγράφεται παντού: access logs του nginx, load balancers και CDN, ιστορικό browser, κεφαλίδες Referer προς τρίτους ιστότοπους, εργαλεία APM και παρακολούθησης. Όποιος μπορεί να διαβάσει ένα από αυτά έχει το token – και μαζί του τη διασύνδεση. Οι αριθμοί τηλεφώνου είναι προσωπικά δεδομένα κατά τον GDPR: η αποθήκευσή τους για εβδομάδες σε logs χωρίς σκοπό είναι ξεχωριστό πρόβλημα συμμόρφωσης.

  • Μεταφέρετε τα tokens σε κεφαλίδα (Authorization) και τα δεδομένα στο σώμα του POST· μετά αλλάξτε το token – το παλιό είναι στα logs.
  • Καταγράφετε μόνο το $uri (διαδρομή χωρίς query string) – ή καθόλου access log για τα endpoints διασύνδεσης.
  • Περιορίστε τη διατήρηση: logrotate (14–30 ημέρες), Docker max-size/max-file· διαγράψτε παλιά logs με μυστικά.
  • Logs αναγνώσιμα μόνο από root/adm· τα logs διασυνδέσεων (pm2, node) περιέχουν συχνά ολόκληρα αιτήματα με κωδικούς – ελέγξτε τα κι αυτά.

2. Εναλλαγή κωδικών και κλειδιών

Ένα μυστικό που δεν αλλάζει ποτέ το ξέρουν τελικά όλοι όσοι είχαν ποτέ πρόσβαση: πρώην υπάλληλοι, συνεργάτες, ένα παλιό laptop, ένα ιστορικό συνομιλίας. Η εναλλαγή περιορίζει πόσο καιρό είναι χρήσιμη μια διαρροή.

  • Πρώτα απογραφή: λίστα όλων των μυστικών – ρόλοι PostgreSQL, admin_passwd, κλειδιά API του Odoo, tokens διασυνδέσεων, SMTP, διαπιστευτήρια πληρωμών/αποστολών/τράπεζας, κλειδιά SSH, tokens cloud – με υπεύθυνο και ημερομηνία τελευταίας αλλαγής.
  • Πότε: αμέσως όταν φεύγει κάποιος με πρόσβαση ή υπάρχει υποψία διαρροής· αλλιώς προγραμματισμένα (π.χ. κάθε 6–12 μήνες για κοινά μυστικά).
  • Πώς χωρίς διακοπή: δημιουργήστε το νέο κλειδί, αλλάξτε τον καταναλωτή, μετά ανακαλέστε το παλιό. Για τον κωδικό βάσης του Odoo αρκεί μια σύντομη επανεκκίνηση.
  • Πού: όχι σε git, όχι σε chat· αρχεία chmod 600/640, password manager ή secret store για την ομάδα.

3. Θύρες: προς τα έξω μόνο 80 και 443

Η κλασική παγίδα: το firewall (ufw) δείχνει «deny» και παρ' όλα αυτά το Odoo είναι προσβάσιμο στη 8069 από το Internet. Το Docker γράφει δικούς του κανόνες iptables για δημοσιευμένες θύρες και παρακάμπτει το ufw. Δημοσιεύστε μόνο σε 127.0.0.1 ή καθόλου, και μπλοκάρετε στην αλυσίδα DOCKER-USER – συν firewall του παρόχου μπροστά από τον server.

4. Η κίνηση μεταξύ servers μπορεί να διαβαστεί

Odoo ↔ PostgreSQL, primary ↔ replica, Odoo ↔ διασυνδέσεις συχνά τρέχουν χωρίς κρυπτογράφηση «επειδή είναι το εσωτερικό δίκτυο». Όμως σε αυτό το δίκτυο βρίσκονται άλλες εικονικές μηχανές, η υποδομή του παρόχου – και διαχειριστές. Όποιος έχει root σε έναν από τους hosts ή πρόσβαση στη διαδρομή του δικτύου μπορεί να καταγράψει την κίνηση με tcpdump: δεδομένα πελατών, τιμολόγια, session cookies, API tokens. Αυτό περιλαμβάνει και έναν ανέντιμο ή απρόσεκτο δικό σας διαχειριστή.

Αν πρέπει να προστατευτούν πολλές υπηρεσίες μαζί, ένα δίκτυο WireGuard μεταξύ των servers είναι η απλούστερη κουβέρτα: όλα μεταξύ των hosts κρυπτογραφούνται, οι υπηρεσίες ακούν μόνο στη διεύθυνση του tunnel.

5. Απέναντι στον εσωτερικό: ελάχιστα δικαιώματα και ιχνηλασιμότητα

  • Προσωπικοί λογαριασμοί αντί για έναν κοινό χρήστη με sudo χωρίς κωδικό· κλειδιά SSH ανά άτομο· αφαιρέστε όσους φεύγουν την ίδια μέρα από όλους τους hosts.
  • Μυστικά αναγνώσιμα μόνο από τον χρήστη της υπηρεσίας (odoo.conf 640, .env 600) – αρχεία ρυθμίσεων και logs με 644 και κωδικούς είναι συνηθισμένα.
  • Καταγράφετε τις εντολές root (auditd) και στέλνετε τα logs κάπου που ο διαχειριστής του server δεν μπορεί να τα αλλάξει.
  • 2FA για την κονσόλα cloud, τον registrar του domain, το Cloudflare, το GitHub – εκεί είναι τα κλειδιά για όλα.
  • Όταν φεύγει κάποιος: αλλάξτε ό,τι μπορούσε να διαβάσει, όχι μόνο τη σύνδεσή του.

Λίστα ελέγχου

  • Όχι tokens/κωδικούς/τηλέφωνα σε URL· access logs χωρίς query strings· διατήρηση ≤ 30 ημέρες.
  • Απογραφή μυστικών με υπεύθυνο και ημερομηνία· εναλλαγή όταν φεύγει κάποιος και προγραμματισμένα.
  • Από έξω μόνο 80/443 (και SSH από γνωστές διευθύνσεις)· θύρες Docker σε 127.0.0.1· κανόνες DOCKER-USER· firewall παρόχου.
  • PostgreSQL με ssl = on, hostssl και db_sslmode = verify-full· αναπαραγωγή και διασυνδέσεις μέσω TLS ή WireGuard.
  • Προσωπικοί λογαριασμοί διαχειριστών, auditd, 2FA σε όλες τις κονσόλες, μυστικά όχι αναγνώσιμα από όλους.
