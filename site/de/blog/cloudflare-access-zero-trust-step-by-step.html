Cloudflare Access (Zero Trust) Schritt für Schritt – und wann es besser ist als ein Passwort

Anmeldung per E-Mail-Code oder SSO vor jeder Website oder jedem Testsystem – ohne eine Zeile Code. Einrichtung in fünf Schritten, Vergleich mit Basic Auth über Pages Functions, Stolperfallen und Odoo-Praxis.

Auf dieser Website gibt es zwei Demo-Seiten mit gleichem Inhalt und unterschiedlichem Schutz: /test/ mit Basic Auth über Cloudflare Pages Functions (ein gemeinsames Passwort, geprüft von einer kleinen Funktion) und /test2/ mit Cloudflare Access (persönliche Anmeldung per E-Mail-Code). Dieser Artikel erklärt Access und wann man welches nimmt.

Was ist Cloudflare Access?

Access ist Teil von Cloudflare Zero Trust. Es steht vor einer Website oder Anwendung und lässt nur durch, wer sich angemeldet hat und von einer Richtlinie erlaubt ist. Anmelden kann man sich per Einmal-Code an die E-Mail-Adresse, über Google, Microsoft, GitHub oder ein Firmen-SSO. Der Free-Tarif erlaubt bis zu 50 Benutzer.

Faustregel: ein Passwort für eine Handvoll Leute – Basic Auth. Personen, Rollen, Protokoll, SSO – Access.

Einrichtung in fünf Schritten

  1. Zero Trust aktivieren. dash.cloudflare.com → Zero Trust → Teamnamen wählen (daraus wird <team>.cloudflareaccess.com) → Tarif Free. Cloudflare kann eine Zahlungsmethode verlangen, der Free-Tarif kostet nichts.
  2. Anmeldemethode. Zero Trust → Settings → Authentication → Login methods → „One-time PIN“ hinzufügen. Optional Google, Microsoft oder GitHub.
  3. Anwendung anlegen. Access → Applications → Add → Self-hosted. Domain und Pfad eintragen, z. B. 2027.pp.ua + test2. Sitzungsdauer wählen (hier 24 h).
  4. Richtlinie. Action „Allow“, Include → „Emails“ (einzelne Adressen) oder „Emails ending in“ (z. B. @firma.de). Ohne passende Richtlinie kommt niemand hinein.
  5. Alle Adressen schützen. Dieselbe Seite ist oft über mehrere Namen erreichbar: eigene Domain, Spiegel-Domains, projekt.pages.dev. Jede davon als weiteres Ziel (Destination) in die Anwendung eintragen.

Genau Schritt 5 wird oft vergessen: Bei der Demo /test2/ war die Seite zunächst nur auf 2027.pp.ua geschützt – über goldberg.pp.ua und goldberg-odoo.pages.dev wäre sie offen gewesen. Darum immer alle Hostnamen prüfen.

Access vor Odoo

  • Stage- und Testsysteme komplett hinter Access legen – Kunden und Tester melden sich mit ihrer E-Mail an, ohne zusätzliche Odoo-Konten zu verraten.
  • Datenbank-Manager (/web/database/*) für die Produktion: eigene Access-Anwendung nur für diesen Pfad, Zugang nur für Administratoren.
  • API, Webhooks, mobile App können keine interaktive Anmeldung: für diese Pfade eine „Bypass“-Richtlinie oder einen Service-Token verwenden.
  • Wichtig: Access schützt nur den Weg über Cloudflare. Ist der Odoo-Server direkt per IP erreichbar, ist der Schutz umgangen – Firewall nur für Cloudflare-IPs öffnen oder Cloudflare Tunnel nutzen und den Header Cf-Access-Jwt-Assertion prüfen.
