Odoo-Betrieb automatisieren: was jeder Schritt spart – und was Sie vom Dienstleister verlangen sollten

Backups mit automatischem Wiederherstellungstest, Monitoring, Staging-Kopien per Befehl, Update- und Upgrade-Pipeline, Branchenvorlagen, Schulungsmaterial: zwölf Automatisierungen für ein Odoo-Projekt auf eigenem Server – jede mit den Stunden und Euro, die sie pro Jahr spart, und warum. Am Ende: was ein Kunde vom Dienstleister verlangen sollte, um das Budget zu senken und die Qualität zu heben, und wie man es prüft.

In unserem Kostenvergleich hat Odoo auf eigenem Server über fünf Jahre gegen Odoo.sh verloren – nicht wegen des Servers, sondern wegen der Stunden drumherum: Administration, Supportfälle, Staging-Kopien, Versionswechsel. Odoo.sh ist günstiger, weil eine Plattform diese Arbeit erledigt. Dasselbe lässt sich für den eigenen Server bauen. Dieser Artikel geht es Schritt für Schritt durch und gibt jedem Schritt einen Preis.

Die Zahlen nutzen das Modell aus unserem Vergleich Odoo und SAP: 5 Anwender, Odoo Community auf eigenem Server, 90 € pro Stunde, 1.000 € pro Tag. Es sind Planungswerte, keine Messungen – die Rechnung steht am Ende, damit Sie Ihre eigenen Werte einsetzen können.

Ausgangslage: was ohne Automatisierung Zeit kostet

  • Administration (Updates, Backups, Monitoring): 24 Stunden im Jahr;
  • Supportfälle („Mail geht nicht“, „Bot schweigt“, „Fehler nach Update“): 16 Stunden im Jahr;
  • Server-Einrichtung ½ Tag, Einführung 8 Tage, Schulung 2 Tage, danach ½ Tag pro Jahr;
  • alle 2–3 Jahre eine neue Odoo-Version: 5 Tage mit OpenUpgrade;
  • über 5 Jahre: 37.300 € – mehr als Odoo.sh (35.670 €).

1. Server als Code

Ein Skript oder Playbook baut den ganzen Server: VPS über die API des Anbieters, DNS, Docker Compose mit Odoo und PostgreSQL, nginx mit HTTPS, Firewall, Backups und Monitoring. Dieselben Dateien bauen Produktion, Staging und einen Ersatzserver.

  • Zeit: ½ Tag → 1 Stunde pro Server; ein Ersatzserver nach Totalausfall in etwa einer Stunde statt einem Tag.
  • Geld: etwa 400 € pro Server, im Notfall mehr – teuer ist die Stunde Stillstand der ganzen Firma.
  • Warum: Von Hand wird kein Server zweimal gleich eingerichtet; die vergessene Firewall-Regel oder der vergessene Backup-Job fällt Monate später auf. Ein Skript ist zugleich die Dokumentation.

2. Backups mit automatischem Wiederherstellungstest

Jede Nacht: Datenbank-Dump und Filestore an einen zweiten Ort (z. B. S3/R2). Jede Nacht oder jede Woche: das neueste Backup wird in einen Wegwerf-Container eingespielt, einige Kennzahlen werden verglichen, das Ergebnis geht in den Admin-Chat.

  • Zeit: etwa 6 Stunden im Jahr manuelle Kontrollen und Test-Wiederherstellungen.
  • Geld: etwa 540 € im Jahr.
  • Warum: Ein Backup, das nie wiederhergestellt wurde, ist eine Hoffnung, kein Backup. Der automatische Test sagt auch, wie lange eine Wiederherstellung dauert – die Zahl, die man im Notfall braucht.

3. Monitoring und Alarme

Ein Bot prüft alle paar Minuten: Odoo antwortet, Plattenplatz, Ablauf des Zertifikats, Mail-Warteschlange, fehlgeschlagene Cron-Jobs, Fehler im Log, Alter des Backups – und schreibt in den Admin-Chat, bevor ein Anwender anruft.

  • Zeit: etwa 5 Stunden im Jahr (2 Administration, 3 Support).
  • Geld: etwa 450 € im Jahr, plus vermiedener Stillstand – 5 Personen, die eine Stunde nicht arbeiten können, kosten mehr als der Bot.
  • Warum: Die meisten Ausfälle kündigen sich an: Die Platte füllt sich über Wochen, das Zertifikat läuft an einem bekannten Datum ab. Ohne Monitoring findet der Anwender das Problem – mit Monitoring der Admin, meist bevor es stört.

4. Staging-Kopie per Befehl

Ein Befehl kopiert die Produktion in eine Testdatenbank und neutralisiert sie: ausgehende Mail, Cron-Jobs, Zahlungsanbieter und Integrationen sind aus, ein „TEST“-Banner erscheint.

  • Zeit: 2–3 Stunden → 10 Minuten pro Kopie; etwa 3 Stunden im Jahr.
  • Geld: etwa 270 € im Jahr – und keine Test-Mails an echte Kunden.
  • Warum: Updates und neue Module sollten auf echten Daten ausprobiert werden. Dauert eine Kopie einen halben Tag, wird auf der Produktion getestet. Ohne Neutralisierung schickt die Kopie Mahnungen an Kunden und doppelte Bot-Nachrichten.

5. Update-Pipeline innerhalb einer Version

Einmal pro Woche: das neueste Image derselben Odoo-Version kommt auf Staging, Tests laufen, dann geht das Image im Wartungsfenster auf die Produktion; das vorige Image und ein Datenbank-Snapshot bleiben für den Rückweg.

  • Zeit: etwa 5 Stunden im Jahr.
  • Geld: etwa 450 € im Jahr.
  • Warum: Sicherheitskorrekturen kommen jede Woche. Von Hand werden sie verschoben – und dann kommen viele Änderungen auf einmal, was riskanter ist. Mit Rückweg ist ein Update kein Abenteuer mehr.

6. Tests und CI für eigene Module

Jede Änderung an eigenen Modulen läuft automatisch durch: Installation auf leerer Datenbank, Tests der kritischen Abläufe (Angebot → Rechnung, Lagerbuchung, DATEV-Export), Code-Prüfungen – auf der aktuellen und der nächsten Odoo-Version.

  • Zeit: etwa 2 Stunden im Jahr Support für Fehler, die Tests gefunden hätten; mehr bei größeren Anpassungen.
  • Geld: etwa 180 € im Jahr, und der Versionswechsel wird günstiger (nächster Abschnitt).
  • Warum: Ein Fehler, den CI findet, kostet Minuten; derselbe Fehler, den die Buchhaltung am Monatsende findet, kostet Stunden und Nerven.

7. Upgrade-Pipeline zur neuen Odoo-Version

Enterprise: die Datenbankkopie geht durch Odoos Upgrade-Service; Community: OpenUpgrade in einem Container. Danach werden die eigenen Module auf der neuen Version gebaut und getestet, alles auf Staging. Ergebnis ist eine Liste dessen, was bricht – lange vor dem eigentlichen Umstellungstag.

  • Zeit: 5 Tage → 2 Tage pro Versionswechsel.
  • Geld: etwa 3.000 € pro Versionswechsel, alle 2–3 Jahre.
  • Warum: Odoo.sh ist hier günstig, weil die Plattform genau das tut. Die meiste Arbeit bei einem Upgrade ist herauszufinden, was bricht; die Pipeline tut das automatisch und jede Woche.

8. Branchenvorlagen statt Start bei null

Einstellungen als Datenmodul: Kontenrahmen (SKR03/SKR04), Steuern, DATEV, Dokumentlayouts, E-Mail-Vorlagen, typische Produkte und Arbeitsplätze – eine Vorlage pro Branche (Handwerk, Großhandel, Laden mit Kasse).

  • Zeit: Einführung 8 → 6 Tage.
  • Geld: etwa 2.000 € pro Projekt.
  • Warum: Zwei Drittel jeder Einführung sind in jeder Firma der Branche gleich. Eine getestete Vorlage stimmt außerdem vom ersten Tag an – keine vergessene Steuereinstellung.

9. Schulungsmaterial: Videos, Checklisten, Texte

Kurze Videos (2–5 Minuten) der eigenen Abläufe mit Transkript in Ihrer Sprache, Checklisten für typische Probleme, eine Seite mit allen Links.

  • Zeit: Schulung 2 → 1 Tag; Auffrischung ½ → ¼ Tag pro Jahr; neue Mitarbeiter lernen allein.
  • Geld: etwa 1.000 € am Anfang, danach 250 € im Jahr.
  • Warum: Ein Trainer erklärt jeder neuen Person dieselben fünf Abläufe. Ein Video tut das nachts, und das Transkript macht es durchsuchbar.

10. Checklisten, Selbsthilfe und Standard-Mailsetup

Für „Mail geht nicht“, „Bot schweigt“, „druckt nicht“: Checklisten für Anwender und Admins, Bot-Befehle für den Admin des Kunden (Status, Mail-Warteschlange, Neustart), Mail überall gleich eingerichtet mit SPF/DKIM/DMARC-Prüfung.

  • Zeit: etwa 3 Stunden im Jahr Support.
  • Geld: etwa 270 € im Jahr.
  • Warum: Die Hälfte aller Supportfälle sind dieselben fünf Probleme. Eine Checkliste löst sie ohne Ticket oder macht aus einem vagen „geht nicht“ ein Ticket mit den richtigen Angaben.

11. Zugänge, Geheimnisse und Dokumentation

Persönliche Konten mit 2FA statt eines gemeinsamen Admins, Geheimnisse in einem Passwortmanager oder Secret-Store – nicht im Repository, eine Admin-Anleitung im Repository: was wo läuft, wie man wiederherstellt, wen man anruft.

  • Zeit: ein neuer Admin bekommt Zugang in 15 Minuten statt 2 Stunden; ein Dienstleisterwechsel dauert 1 Tag statt 3–5.
  • Geld: pro Jahr schwer zu beziffern; beim Dienstleisterwechsel 2.000–4.000 €.
  • Warum: Ohne Dokumentation hängt der Kunde an einer Person. Dokumentation und saubere Zugänge machen den Dienstleister austauschbar – was auch die Preise ehrlich hält.

12. Mehrere kleine Kunden auf einem Server (optional)

Kleine Installationen teilen sich einen größeren Server, jede mit eigener Datenbank, Domain und eigenem Backup; Monitoring und Updates laufen einmal für alle.

  • Zeit: die Administration pro Kunde sinkt weiter.
  • Geld: Hosting etwa 360 → 150 € im Jahr pro Kunde.
  • Warum: So arbeitet Odoo.sh mit seinen geteilten Workern. Der Preis: weniger Isolation – ein Kunde mit schweren Berichten kann die anderen bremsen; für sensible Daten bleibt ein eigener Server die bessere Wahl.

Was ein Kunde vom Dienstleister verlangen sollte – und wie man es prüft

Die meisten Punkte kosten den Dienstleister wenig, sobald sie einmal eingerichtet sind – und sie entscheiden, ob Sie für Stunden oder für Ergebnisse zahlen. Schreiben Sie sie in den Vertrag und prüfen Sie sie, nicht nur einmal:

ForderungWie prüfen
Alles in einem Git-Repository, das Ihnen gehört – Module, Konfiguration, Docker-Dateien, Skripte.Sie haben Eigentümerrechte im Repository; lassen Sie ein Deployment aus dem Repository machen, während Sie zusehen. → Schritt für Schritt
Reproduzierbarer Server (Server als Code).Lassen Sie einen frischen Staging-Server aus dem Repository bauen – und stoppen Sie die Zeit. → Schritt für Schritt
Backups an einem zweiten Ort und automatischer Wiederherstellungstest mit Bericht.Fordern Sie die letzten Testberichte an; nennen Sie ein zufälliges Datum und lassen Sie dieses Backup auf Staging einspielen. → Schritt für Schritt
Monitoring mit Alarmen, und Sie sind im Alarm-Chat.Sie sehen die Alarme selbst; fordern Sie die Liste der Alarme des letzten Monats und was getan wurde. → Schritt für Schritt
Neutralisierte Staging-Kopie vor jedem Update.Schicken Sie sich aus Staging eine Test-Mail – sie darf das System nicht verlassen. → Schritt für Schritt
Tests und CI für jedes eigene Modul, Übernahme nur bei Grün.Schauen Sie in die Pipeline: grüne Builds, Tests für die kritischen Abläufe (Angebot → Rechnung, DATEV-Export). → Schritt für Schritt
So wenig eigener Code wie möglich: zuerst Standard oder OCA, eine Begründung für jedes eigene Modul.Liste der eigenen Module mit Grund und Umfang; jedes Modul hinterfragen, das nur Felder umbenennt. → Schritt für Schritt
Ein Upgrade-Plan: welche Version wann, was bricht, was es kostet.Fordern Sie das Test-Upgrade einer Kopie auf die nächste Version und dessen Bericht. → Schritt für Schritt
Festumfang mit Abnahmekriterien statt offener Stunden.Jeder Punkt hat einen schriftlichen Testfall; Sie nehmen Punkt für Punkt ab. → Schritt für Schritt
Dokumentation und Übergabe: Admin-Anleitung, Zugänge, Kontakte.Lassen Sie eine dritte Person (oder einen anderen Dienstleister) nur mit der Anleitung ein Backup wiederherstellen. → Schritt für Schritt
Persönliche Konten mit 2FA, keine Geheimnisse im Repository.Liste der Konten und wer sie hat; ein Secret-Scan des Repositorys (z. B. gitleaks). → Schritt für Schritt
Schulungsmaterial in Ihrer Sprache: Videos, Checklisten.Ein neuer Mitarbeiter erledigt eine typische Aufgabe nur mit dem Material. → Schritt für Schritt
Reaktionszeiten und ein Monatsbericht der Stunden nach Kategorie (Support, Administration, Entwicklung).Vergleichen Sie die Kategorien Quartal für Quartal – Automatisierung muss sich als sinkende Support- und Admin-Stunden zeigen. → Schritt für Schritt
Ausstiegsklausel: Datenexport und Übergabe am Vertragsende.Machen Sie einmal einen Probeexport: Datenbank, Filestore, Repository – kann jemand anderes es starten? → Schritt für Schritt

Fazit

Odoo auf eigenem Server ist nur dann teuer, wenn Menschen tun, was Skripte tun können. Zwölf Automatisierungen kosten einen Dienstleister einmal 15–25 Tage und sparen einer kleinen Firma etwa die Hälfte der laufenden Kosten – über fünf Jahre rund 18.000 €, sodass der eigene Server unter Odoo.sh landet. Als Kunde müssen Sie nicht jedes Skript verstehen: Es reicht, die Ergebnisse oben zu verlangen und regelmäßig zu prüfen. So bauen wir Odoo-Projekte für Unternehmen in Deutschland, Österreich und der Schweiz.
