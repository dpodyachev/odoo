PgBouncer für Odoo: Transaction Pooling, ohne Bus und queue_job zu zerstören

Warum viele Odoo-Worker einen Connection Pooler brauchen, warum Transaction Pooling die Live-Benachrichtigungen von Odoo und OCA queue_job bei naiver Einrichtung lahmlegt, und eine funktionierende pgbouncer.ini mit Session Pooling für die Datenbank postgres – dazu Dimensionierung, Überwachung und Fehlersuche.

Mit mehreren Odoo-Servern oder Hunderten Workern explodiert die Zahl der Datenbankverbindungen: Jeder Odoo-Prozess hält einen eigenen Pool mit bis zu db_maxconn Verbindungen. PostgreSQL bezahlt jede Verbindung mit einem Prozess und RAM – und ab einigen Hundert aktiven Verbindungen wird es spürbar langsamer. PgBouncer sitzt dazwischen: Odoo öffnet so viele billige Client-Verbindungen, wie es will, PostgreSQL sieht nur einen kleinen Pool.

Kurzfassung: Die Odoo-Datenbanken mit pool_mode = transaction, die Datenbank postgres mit pool_mode = session (dort läuft LISTEN imbus des Odoo-Bus) und der OCA-queue_job-Runner direkt zu PostgreSQL über jobrunner_db_host/port. Anders eingerichtet hören Chat, Benachrichtigungen und Job-Verarbeitung still auf zu funktionieren.

Pooling-Modi – und was Odoo braucht

  • session: Eine Server-Verbindung gehört dem Client, bis er sich trennt. Sicher, spart bei Odoos langlebigen Verbindungen aber fast nichts.
  • transaction: Eine Server-Verbindung nur für die Dauer einer Transaktion. Hier liegt der Gewinn: Hunderte untätige Odoo-Verbindungen teilen sich wenige Dutzend echte.
  • statement: keine Transaktionen aus mehreren Anweisungen – für Odoo unbrauchbar.
  • Normale Odoo-Anfragen funktionieren im Transaktionsmodus: Jede Anfrage ist eine Transaktion, psycopg2 sendet die Isolationsstufe mit BEGIN, Odoo nutzt keine serverseitigen Prepared Statements.

Die zwei Fallen

  • Odoo-Bus (Live-Chat, Benachrichtigungen, Dialog): Der Gevent-Prozess öffnet eine Verbindung zur Datenbank postgres und führt LISTEN imbus aus (Quelle: addons/bus/models/bus.py). LISTEN funktioniert nur in einer Session – im Transaktionsmodus gehen die Benachrichtigungen verloren.
  • OCA queue_job: Der Job-Runner führt LISTEN queue_job aus und hält einen Session-Advisory-Lock (pg_try_advisory_lock), damit nur ein Runner arbeitet. Beides braucht eine Session – der Runner bekommt eigene Verbindungsdaten: jobrunner_db_host / jobrunner_db_port.

Beispiel: 4 Odoo-Server × 33 Worker, DB-Server mit 32 Kernen. max_client_conn = 2000, default_pool_size = 64–100, max_db_connections = 150, PostgreSQL max_connections = 200. Ohne PgBouncer hätte PostgreSQL mehrere Hundert bis Tausende Verbindungen gebraucht.

Überwachung

Die wichtigste Spalte ist cl_waiting in SHOW POOLS: Clients, die auf eine freie Server-Verbindung warten. Dauerhaft über null = Pool zu klein oder lange Transaktionen (lange Cron-Jobs, Berichte) belegen ihn. maxwait zeigt, wie lange der älteste wartet.

Fehlersuche

  • Chat-Nachrichten und Benachrichtigungen erscheinen erst nach Neuladen → Die Datenbank postgres läuft im Transaktionsmodus; für sie pool_mode=session setzen.
  • queue_job-Jobs bleiben auf „enqueued“ → Der Runner verbindet sich über Transaction Pooling; jobrunner_db_port auf PostgreSQL oder einen Session-Eintrag setzen.
  • no more connections allowed (max_client_conn) → max_client_conn erhöhen; Odoo-Prozesse × db_maxconn prüfen.
  • query_wait_timeout → Pool erschöpft: default_pool_size vorsichtig erhöhen oder die langen Transaktionen finden (pg_stat_activity).
  • DROP DATABASE / Restore scheitert: database is being accessed → PAUSE mydb; oder KILL mydb; in der PgBouncer-Konsole oder direkt auf Port 5432 arbeiten.
  • Der Odoo-Datenbankmanager zeigt eine neue Datenbank nicht → Wildcard-Eintrag * vorhanden? Mit list_db = False ohnehin egal.

Wann man es nicht braucht

Ein Odoo-Server mit 10–20 Workern neben PostgreSQL: Die Zahl der Verbindungen ist klein, PgBouncer bringt nur eine zusätzliche Komponente. Es lohnt sich mit mehreren Odoo-Servern, vielen Workern, max_connections im hohen dreistelligen Bereich – unser Rechner zeigt ab 500 einen Hinweis.
