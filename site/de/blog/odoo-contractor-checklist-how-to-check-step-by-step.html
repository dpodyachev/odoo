Die Checkliste für Kunden erklärt: wie man jeden Punkt prüft – Schritt für Schritt für Einsteiger

„Sie haben Eigentümerrechte im Repository“ – aber wo sieht man das bei GitHub, GitLab oder Bitbucket? Vierzehn Prüfungen aus unserer Checkliste für Dienstleister, erklärt für Menschen ohne IT-Hintergrund: was jede bedeutet, wo man klickt, wie es aussieht, gute Zeichen und Warnzeichen, mit Links zur offiziellen Dokumentation.

In unserem Artikel über die Automatisierung des Odoo-Betriebs haben wir vierzehn Dinge aufgezählt, die ein Kunde vom Dienstleister verlangen sollte – und wie man sie prüft. „Wie prüfen“ ist leicht geschrieben und schwer getan, wenn man nie ein Git-Repository oder einen Backup-Bericht gesehen hat. Diese Anleitung geht jeden Punkt so durch, wie man ihn einem neuen Kollegen erklären würde: was er bedeutet, wo man schaut, was man sehen sollte.

Die Bilder sind vereinfachte schematische Bildschirme, keine Screenshots: Menünamen folgen GitHub, Odoo und gängigen Werkzeugen, können sich je nach Version und Sprache aber leicht unterscheiden. Wo mehrere Produkte üblich sind (GitHub, GitLab, Bitbucket), nennen die Schritte alle.

1. Das Repository gehört Ihnen

Der gesamte Code, die Konfiguration und die Skripte Ihres Odoo liegen in einem Git-Repository – einem Ordner mit vollständiger Historie auf einer Plattform wie GitHub, GitLab oder Bitbucket. Wer Eigentümer ist, entscheidet, wer Zugang hat, und kann den Code mitnehmen. Das muss Ihre Firma sein, nicht der Dienstleister oder einer seiner Mitarbeiter.

  1. Lassen Sie sich den Link zum Repository geben. Der Teil nach dem Plattformnamen ist der Eigentümer: github.com/ihre-firma/odoo gehört der Organisation ihre-firma, github.com/max-dev/odoo dem persönlichen Konto von max-dev.
  2. GitHub: Repository öffnen ‣ Settings ‣ Collaborators and teams. In einem Organisations-Repository sehen Sie Rollen (Read, Triage, Write, Maintain, Admin); die Eigentümer der Organisation stehen unter Organisation ‣ People ‣ Filter Owner. Ein Repository eines persönlichen Kontos hat nur einen Eigentümer – dieses Konto.
  3. GitLab: Projekt ‣ Manage ‣ Members – Rollen von Guest bis Owner; das Projekt sollte in einer Gruppe liegen, die Ihnen gehört.
  4. Bitbucket: Repositories gehören einem Workspace; prüfen Sie Workspace settings ‣ Benutzer und Gruppen (Sie als Administrator) und Repository settings ‣ Repository permissions.
  5. Ebenfalls möglich: Azure DevOps oder ein selbst betriebenes Gitea/GitLab – die Frage bleibt dieselbe: Wer ist Administrator?
  6. Lassen Sie dann ein Deployment machen, während Sie zusehen: Die Version auf dem Server muss aus diesem Repository kommen (gleiche Commit-Nummer in der Pipeline und auf dem Server).
  • Gut: eine Organisation oder ein Workspace auf den Namen Ihrer Firma; Sie sind Owner/Administrator; der Dienstleister hat Write oder Maintainer.
  • Warnzeichen: Das Repository liegt im persönlichen Konto des Dienstleisters oder eines Mitarbeiters; Sie haben gar keinen Zugang; „wir deployen von unserem Laptop“. Lösung: Repository an Ihre Organisation übertragen lassen (GitHub: Settings ‣ Transfer ownership).

2. Der Server lässt sich aus dem Repository neu bauen

„Server als Code“ heißt: Der Server wird nicht von Hand eingerichtet, sondern durch Dateien im Repository – z. B. docker-compose.yml für Odoo und PostgreSQL, Ansible oder Terraform für den Server selbst. Dann kann jeder einen identischen Server bauen, und ein Totalausfall ist eine Frage von einer Stunde.

  1. Schauen Sie ins Repository: Gibt es Dateien wie docker-compose.yml, einen Ordner ansible/ oder terraform/, eine README.md mit „wie man einen Server baut“?
  2. Bitten Sie den Dienstleister, einen frischen Staging-Server aus dem Repository zu bauen – auf einer neuen, leeren Maschine.
  3. Messen Sie die Zeit von der leeren Maschine bis zur Anmeldeseite von Odoo und notieren Sie sie: Das ist Ihre Wiederherstellungszeit im Notfall.
  4. Prüfen Sie, dass der neue Server dieselbe Odoo-Version und dieselben Module hat wie die Produktion (Einstellungen ‣ Info / Apps).
  • Gut: ein frischer Server in weniger als einem Tag, ohne „da muss ich mich noch erinnern …“.
  • Warnzeichen: „das geht nur auf dem bestehenden Server“, handschriftliche Notizen, manuelle Schritte, die nicht im Repository stehen.

3. Backups an einem zweiten Ort – und ein Wiederherstellungstest

Ein Backup ist eine Kopie der Datenbank und der Anhänge (Filestore). Zweiter Ort heißt anderes Rechenzentrum oder anderer Anbieter – ein Backup auf demselben Server brennt mit ab. Erst ein Wiederherstellungstest beweist, dass die Kopie brauchbar ist.

  1. Fragen Sie, wo die Backups liegen und wie viele Tage aufbewahrt werden. Erwartung: täglich, mindestens 14–30 Tage, außerhalb des Servers.
  2. Lassen Sie sich die Berichte der letzten Wiederherstellungstests zeigen – E-Mails oder Chatnachrichten mit Datum, Größe, Dauer und einer Kennzahl aus den Daten (Zahl der Rechnungen, neuester Eintrag).
  3. Nennen Sie ein zufälliges Datum der letzten Wochen und lassen Sie dieses Backup auf Staging einspielen.
  4. Melden Sie sich auf diesem Staging an und schauen Sie sich das neueste Dokument dieses Tages an – passt es zu Ihrer Erinnerung?
  • Gut: Berichte jeden Tag oder jede Woche; Wiederherstellung eines beliebigen Datums in ein, zwei Stunden; die Dauer ist bekannt.
  • Warnzeichen: „Backups werden gemacht“ ohne Nachweis; die einzige Kopie auf demselben Server; niemand weiß, wie lange eine Wiederherstellung dauert.

4. Monitoring mit Alarmen – und Sie sehen sie

Monitoring ist ein Programm, das das System alle paar Minuten prüft und Alarm schlägt: Odoo antwortet nicht, die Platte ist voll, das Zertifikat läuft ab, E-Mails hängen fest. Die Alarme gehen in einen Chat oder per E-Mail – und Sie sollten dabei sein.

  1. Lassen Sie sich in den Alarm-Chat (Telegram, Teams, Slack) oder die Alarm-Mailingliste aufnehmen.
  2. Fordern Sie die Liste der Alarme des letzten Monats an und was jeweils getan wurde.
  3. Prüfen Sie, dass das Typische überwacht wird: Odoo erreichbar, Plattenplatz, Zertifikat, Mail-Warteschlange, fehlgeschlagene geplante Aktionen, Alter des letzten Backups.
  4. Werkzeuge, von denen Sie hören könnten: Uptime Kuma, Healthchecks.io, Zabbix, Grafana, eigene Bots – wichtiger als das Werkzeug ist, dass jemand reagiert.
  • Gut: Warnungen Tage vor einem Problem (Platte, Zertifikat); zu jedem Alarm eine kurze Antwort „Ursache – behoben“.
  • Warnzeichen: Sie erfahren von Ausfällen durch Ihre Mitarbeiter; niemand kann einen Alarm des letzten Monats zeigen.

Mehr: Uptime Kuma ↗ · Healthchecks.io (cron jobs) ↗

5. Eine neutralisierte Staging-Kopie vor jedem Update

Staging ist eine Kopie Ihres Odoo zum Testen. Neutralisiert heißt: Sie kann keine E-Mails an Kunden senden, geplante Aktionen (Mahnungen, Abos) und Zahlungen sind aus, und ein farbiges Banner zeigt, dass es ein Testsystem ist. Updates werden zuerst dort ausprobiert.

  1. Lassen Sie sich die Staging-Adresse geben und melden Sie sich an. Oben sollten Sie ein Banner sehen (roter Streifen oder „TEST“).
  2. Erstellen Sie dort ein Testdokument und schicken Sie es per E-Mail an sich selbst. Es darf nicht ankommen – es sollte mit Fehler in der Liste ausgehender Mails landen oder in einem Mail-Fänger wie Mailpit.
  3. Prüfen Sie im Staging: Einstellungen ‣ Technisch ‣ Geplante Aktionen – größtenteils inaktiv; Postausgangsserver – keiner aktiv.
  4. Fragen Sie, wann Staging zuletzt aus der Produktion aufgefrischt wurde und welches Update darauf getestet wurde.
  • Gut: Ihre Test-Mail kommt nicht an; Staging ist nicht älter als das letzte Update.
  • Warnzeichen: Die Test-Mail kommt an (Kunden würden Mahnungen aus Staging bekommen); „wir testen direkt auf der Produktion“.

6. Tests und CI für eigene Module

CI (Continuous Integration) ist ein Roboter, der jede Änderung automatisch prüft, bevor sie übernommen wird: installiert das Modul, führt Tests wichtiger Abläufe aus, prüft den Codestil. Bei GitHub erscheint das als grüne Haken oder rote Kreuze neben jeder Änderung.

  1. GitHub: Repository ‣ Actions (Liste der Läufe) und ‣ Pull requests ‣ ein Request ‣ Checks. GitLab: Build ‣ Pipelines. Bitbucket: Pipelines.
  2. Schauen Sie sich die letzten zehn Änderungen an: Sind sie grün? Wer hat rote übernommen?
  3. Prüfen Sie, dass das Übernehmen ohne grüne Checks gesperrt ist (GitHub: Settings ‣ Branches / Rules – required status checks).
  4. Fragen Sie, welche Geschäftsabläufe getestet werden – z. B. Angebot → Rechnung, Lagerbuchung, DATEV-Export – und ob die Tests auch auf der nächsten Odoo-Version laufen.
  • Gut: jede Änderung hat Prüfungen; Tests für Ihre kritischen Abläufe; Übernahme nur bei Grün.
  • Warnzeichen: gar keine Actions/Pipelines; regelmäßig rote Builds, die trotzdem übernommen werden.

Mehr: GitHub Actions ↗ · GitHub: protected branches ↗ · GitLab: pipelines ↗ · Bitbucket Pipelines ↗

7. So wenig eigener Code wie möglich

Jedes eigene Modul kostet zweimal Geld: wenn es geschrieben wird und bei jedem Versionswechsel. Oft kann der Standard, Odoo Studio oder ein freies Community-Modul (OCA) dasselbe. Ein guter Dienstleister kann jedes eigene Modul begründen.

  1. Fordern Sie eine Liste der eigenen Module mit je einem Satz: warum es existiert und warum Standard oder OCA nicht reichen.
  2. Fragen Sie nach der Größe in Codezeilen (z. B. mit dem Werkzeug cloc gezählt) – sie zeigt, wo die Upgrade-Kosten liegen werden.
  3. Suchen Sie zu jedem Modul kurz selbst: Odoo Apps Store und OCA auf GitHub – gibt es etwas Fertiges?
  4. Hinterfragen Sie Module, die nur ein Feld hinzufügen oder Beschriftungen ändern – das können Studio oder Einstellungen.
  • Gut: wenige Module, jedes mit klarem Grund; Fehlerkorrekturen gehen auch an OCA/Odoo (dann verschwinden sie später).
  • Warnzeichen: Dutzende Module, die niemand erklären kann; Kopien ganzer Standardmodule.

Mehr: OCA on GitHub ↗ · Odoo Apps store ↗ · cloc (count lines of code) ↗

8. Ein Upgrade-Plan zur nächsten Version

Odoo bringt jedes Jahr eine neue Version und unterstützt nur die letzten drei. Früher oder später muss jede Installation umziehen. Ein Upgrade-Plan sagt wann, was bricht und was es kostet – auf Basis eines Test-Upgrades einer Kopie, nicht geschätzt.

  1. Fragen Sie, welche Odoo-Version Sie nutzen und bis wann sie unterstützt wird (Odoos Seite „supported versions“).
  2. Fordern Sie ein Test-Upgrade einer Kopie der Produktion auf die nächste Version: Enterprise über Odoos Upgrade-Service, Community über OpenUpgrade.
  3. Lesen Sie den Bericht: Dauer, welche eigenen Module funktionieren, welche angepasst werden müssen und wie lange das dauert.
  4. Lassen Sie sich auf Basis dieses Berichts ein Angebot mit Termin machen – und eine Testphase auf Staging vor der echten Umstellung.
  • Gut: ein schriftlicher Plan mit Terminen und Kosten, auf Basis eines echten Testlaufs.
  • Warnzeichen: „wir sehen, wenn es so weit ist“; die Version wird schon nicht mehr unterstützt.

Mehr: Odoo: supported versions ↗ · Odoo: upgrade ↗ · OpenUpgrade (OCA) ↗

9. Festumfang mit Abnahmekriterien

Statt „wir arbeiten und rechnen die Stunden ab“ wird jeder Punkt des Projekts mit einem Testfall beschrieben – was funktionieren muss, damit Sie abnehmen können. Ein übliches Format ist Gegeben – Wenn – Dann.

  1. Fordern Sie die Liste der Punkte mit je einem Testfall an, bevor die Arbeit beginnt.
  2. Prüfen Sie, dass die Testfälle in Ihrer Sprache und ohne IT-Wissen prüfbar sind („Gegeben … Wenn … Dann …“).
  3. Nehmen Sie Punkt für Punkt ab: Test selbst auf Staging machen, dann freigeben (E-Mail oder Haken im Projektplan).
  4. Änderungen des Umfangs: neuer Punkt mit eigenem Testfall und Preis – nicht versteckt in „Zusatzstunden“.
  • Gut: Sie wissen, wofür Sie zahlen und wann ein Punkt fertig ist.
  • Warnzeichen: nur ein Stundenbudget; „fertig“ ohne etwas, das Sie testen könnten.

Mehr: Given – When – Then ↗

10. Dokumentation und Übergabe

Die Admin-Anleitung beantwortet die Fragen eines Notfalls: was wo läuft, wie man wiederherstellt, wer welche Zugänge hat, wen man anruft. Sie gehört ins Repository (z. B. README.md), damit sie bei Ihnen bleibt.

  1. Öffnen Sie das Repository und suchen Sie README.md oder einen Ordner docs/: Gibt es Abschnitte zu Servern, Backups und Wiederherstellung, Zugängen, Kontakten?
  2. Der echte Test: Bitten Sie eine dritte Person (einen IT-kundigen Kollegen oder einen anderen Dienstleister), nur mit dieser Anleitung ein Backup auf einer Testmaschine wiederherzustellen.
  3. Notieren Sie, wo sie hängen geblieben ist – jeder Punkt ist eine Lücke in der Dokumentation.
  4. Einmal im Jahr oder nach großen Änderungen wiederholen.
  • Gut: Die dritte Person schafft es, ohne den Dienstleister anzurufen.
  • Warnzeichen: „das ist alles in meinem Kopf“; Dokumentation außerhalb Ihrer Reichweite (Wiki des Dienstleisters).

11. Persönliche Konten mit 2FA – keine Geheimnisse im Repository

Jeder hat sein eigenes Konto – in Odoo, auf dem Server, bei GitHub – geschützt mit Zwei-Faktor-Authentifizierung (2FA: Passwort plus Code vom Telefon). Passwörter und Schlüssel (Geheimnisse) liegen in einem Passwortmanager oder Secret-Store, nie im Code.

  1. GitHub-Organisation: People zeigt die Mitglieder und ob 2FA aktiv ist; Settings ‣ Authentication security kann 2FA für alle verlangen. GitLab: Gruppeneinstellungen ‣ 2FA verlangen.
  2. Fordern Sie die Liste aller Konten an (Odoo-Admins, Server, Git, Hosting, DNS) und wer welches nutzt. Gemeinsame Konten wie „admin“ für mehrere Personen: Warnzeichen.
  3. Entfernen Sie ausgeschiedene Personen – sie erscheinen in den Listen oben.
  4. Lassen Sie das Repository auf Geheimnisse scannen (GitHub secret scanning oder das Werkzeug gitleaks) und sich das Ergebnis zeigen.
  5. In Odoo: Benutzer mit Administratorrechten sollten 2FA nutzen (Benutzereinstellungen ‣ Kontosicherheit).
  • Gut: jedes Konto gehört einer Person; überall 2FA; der Scan findet keine Geheimnisse.
  • Warnzeichen: ein Admin-Passwort für alle; Passwörter in E-Mails oder im Repository; ehemalige Mitarbeiter haben noch Zugang.

12. Schulungsmaterial in Ihrer Sprache

Kurze Videos und Texte Ihrer Abläufe (keine allgemeinen Odoo-Videos) in der Sprache Ihrer Mitarbeiter, dazu Checklisten für typische Probleme. Ein neuer Mitarbeiter sollte damit die Alltagsaufgaben erledigen können.

  1. Fordern Sie die Liste des Materials an: welche Abläufe, welche Sprache, wo es liegt (es sollte bei Ihnen liegen).
  2. Test: Geben Sie einem neuen Mitarbeiter eine typische Aufgabe (z. B. Rechnung aus einer Lieferung erstellen) und nur das Material – keine Hilfe.
  3. Notieren Sie, wo er hängen geblieben ist; der Dienstleister ergänzt ein Video oder einen Satz.
  4. Prüfen Sie, dass das Material nach Änderungen und Upgrades aktualisiert wird.
  • Gut: Die Aufgabe gelingt allein mit dem Material; Videos von 2–5 Minuten mit Transkript.
  • Warnzeichen: nur Links zu allgemeinen Odoo-Videos; Material in einer Sprache, die Ihr Team nicht nutzt.

13. Reaktionszeiten und ein Monatsbericht

Ein kurzer Monatsbericht zeigt die Stunden nach Kategorie: Support (etwas geht nicht), Administration (Updates, Backups), Entwicklung (neue Funktionen). Wenn der Dienstleister automatisiert, müssen Support und Administration mit der Zeit sinken – der Bericht macht das sichtbar.

  1. Vereinbaren Sie Reaktionszeiten im Vertrag (z. B. 4 Arbeitsstunden bei „Odoo ist weg“, 2 Tage bei Fragen).
  2. Fordern Sie einen Monatsbericht mit Stunden je Kategorie und der Liste der Tickets.
  3. Jedes Quartal: Kategorien vergleichen. Sinkende Support- und Admin-Stunden = Automatisierung wirkt; steigende = nach dem Grund fragen.
  4. Prüfen Sie einige Tickets: Wurde die Reaktionszeit eingehalten?
  • Gut: jeden Monat dieselben Kategorien; erkennbare Trends.
  • Warnzeichen: eine Pauschale „IT-Leistungen“ ohne Aufschlüsselung; Support-Stunden, die jedes Quartal wachsen.

14. Ausstiegsklausel und Probeexport

Am Vertragsende müssen Sie alles bekommen, was nötig ist, um mit jemand anderem weiterzumachen: die Datenbank, die Anhänge (Filestore), das Repository und die Anleitung. Der Vertrag sagt das – und ein Probeexport zeigt, dass es funktioniert.

  1. Schreiben Sie in den Vertrag: Export von Datenbank, Filestore und Repository innerhalb weniger Tage, in Standardformaten, ohne Zusatzkosten.
  2. Machen Sie einmal einen Probeexport: Lassen Sie sich die Dateien geben (oder laden Sie selbst ein Backup herunter – bei Odoo Online im Datenbankmanager).
  3. Geben Sie den Export einer dritten Person oder einem anderen Dienstleister: Kann er damit Odoo auf einer Testmaschine starten?
  4. Prüfen Sie das Ergebnis: Sind die neuesten Dokumente da und die Anhänge (PDFs, Bilder)?
  • Gut: Odoo läuft innerhalb eines Tages woanders mit Ihren Daten.
  • Warnzeichen: „der Export kostet extra“; Daten nur in Formaten des Dienstleisters; Anhänge fehlen.

Mehr: Odoo Online: database management (download a backup) ↗ · PostgreSQL: SQL dump ↗

Fazit

Keine dieser Prüfungen braucht IT-Wissen – nur einen Link, eine Frage und die Bereitschaft hinzuschauen. Machen Sie die erste Runde mit dem Dienstleister, notieren Sie die Ergebnisse und wiederholen Sie die wichtigsten Prüfungen (Backup-Wiederherstellung, Alarm-Chat, Probeexport) einmal im Jahr. Ein guter Dienstleister begrüßt das, denn es zeigt, dass die Arbeit ordentlich gemacht ist. So arbeiten wir mit Kunden in Deutschland, Österreich und der Schweiz und zeigen jeden Punkt auf Wunsch.
