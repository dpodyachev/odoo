pg_dump und pg_restore für Odoo: alle Varianten – Docker, systemd, entfernter Server, Filestore

Wie man eine Odoo-Datenbank sichert und wiederherstellt – egal ob PostgreSQL in Docker, als Systemdienst oder auf einem anderen Server läuft: Formate, parallele Jobs, einzelne Tabellen, Filestore, das ZIP aus dem Datenbankmanager, ein nächtliches Skript mit Rotation und die typischen Fehlermeldungen.

„Mach mal ein Backup“ klingt nach einem Befehl. In der Praxis hängt der Befehl davon ab, wo PostgreSQL läuft: in einem Docker-Container, als normaler Systemdienst (systemd) oder auf einem separaten bzw. Cloud-Datenbankserver. Jede Variante hat ihre Fallen – ein fehlendes -T, die falsche Client-Version, Peer-Authentifizierung, ein Ordner, in den der Benutzer postgres nicht schreiben darf. Hier alle Varianten nebeneinander, mit Befehlen zum Kopieren.

Kurzfassung: pg_dump -Fc (Custom-Format) ist der richtige Standard. Den Filestore mitsichern – ohne ihn fehlen in Odoo alle Anhänge. In eine neue Datenbank einspielen und die Namen tauschen, das Restore-Log auf ERROR prüfen und das Einspielen regelmäßig testen.

Schritt 0: herausfinden, wie PostgreSQL läuft

Wichtig: db_host in der odoo.conf sagt, wohin sich Odoo verbindet. localhost in einem Container ist der Container selbst, db meist der Name des Compose-Dienstes, eine IP-Adresse ein anderer Server.

PostgreSQL als Systemdienst (systemd, ohne Docker)

  • Lokaler Socket = Peer-Authentifizierung: PostgreSQL prüft den Linux-Benutzernamen. Deshalb funktioniert sudo -u postgres ohne Passwort, pg_dump -U odoo als root aber nicht.
  • > statt -f bei sudo -u postgres: die Umleitung öffnet Ihre Shell (root), also geht jeder Zielordner.
  • Mehrere Cluster auf einer Maschine (altes 14 und neues 16): pg_lsclusters zeigt sie, --cluster 16/main wählt den richtigen samt passenden Programmen.

PostgreSQL in Docker

  • -T bei docker compose exec (bzw. -i ohne -t bei docker exec) – sonst wird der Dump unbemerkt beschädigt und scheitert erst beim Einspielen.
  • Das offizielle Odoo-Image enthält ebenfalls einen PostgreSQL-Client – oft aber einen älteren als der Server. Meldet pg_dump einen Versionskonflikt, im Datenbank-Container oder in einem Wegwerf-Container postgres:NN mit der Server-Version ausführen.
  • Die Volume-Dateien (/var/lib/postgresql/data) einer laufenden Datenbank nicht einfach kopieren – das ist kein konsistentes Backup.

Datenbank auf einem anderen Server oder als Managed Service (RDS, DigitalOcean, Hetzner …)

Auch hier gilt die Versionsregel: der pg_dump-Client muss mindestens die Server-Version haben. Auf einem alten Arbeitsrechner ist der Client oft älter – ein postgres:NN-Container löst das ohne Installation.

pg_dump hält Odoo nicht an: es liest einen konsistenten Schnappschuss, während die Benutzer weiterarbeiten. Es blockiert aber Schemaänderungen – ein Modul-Update (-u) wartet, bis der Dump fertig ist. Bei großen Datenbanken verzögert ein langer Dump auch das Vacuum – also nachts laufen lassen.

Einspielen

  • -T template0 -E UTF8: eine saubere Datenbank mit der richtigen Kodierung; das Standard-Template kann Extras enthalten.
  • --no-owner --role=odoo: die Objekte gehören dem Odoo-Benutzer, auch wenn der Quellserver einen anderen Rollennamen hatte.
  • -j 4 (Anzahl CPU-Kerne): beschleunigt vor allem den Aufbau der Indizes – nur mit Datei, nicht über stdin.
  • Eine eingespielte Produktionskopie verschickt E-Mails und führt Cron-Jobs aus – vor dem Start von Odoo neutralisieren (siehe Artikel zum Einspielen auf Stage).

Einzelne Tabellen, Inhaltsverzeichnis, Ausschlüsse

Eine einzelne Tabelle direkt in die Produktion einzuspielen klappt in Odoo fast nie sauber: Fremdschlüssel, Sequenzen und abhängige Tabellen passen nicht. Sicherer: in eine Hilfsdatenbank einspielen, vergleichen und dann genau die benötigten Zeilen per SQL übernehmen.

Odoo: der Filestore gehört zum Backup

Eine Datenbank ohne ihren Filestore öffnet sich, aber alle Anhänge, Produktbilder und gespeicherten PDFs fehlen („file not found“ im Log). Datenbank und Filestore sollten vom selben Zeitpunkt stammen – erst der Dump, dann der Filestore, beides im selben Skript.

Das ZIP aus dem Datenbankmanager von Hand einspielen

Das ZIP aus /web/database/manager enthält einen Plain-SQL-Dump und den Filestore. Bei großen Datenbanken scheitert das Hochladen im Browser (Zeit- und Größenlimits) – von Hand entpackt klappt es immer:

Nächtliches Backup mit Prüfung und Rotation

  • set -euo pipefail: scheitert pg_dump, bricht das Skript ab, und das || mail in der crontab meldet es.
  • pg_restore -l prüft schnell, dass die Datei ein lesbarer Dump ist – nicht, dass sich die Daten sauber einspielen lassen. Dafür: regelmäßiges Test-Einspielen auf Stage.
  • Kopien auch außerhalb des Servers aufbewahren (rsync, R2/S3) – ein Backup auf derselben Platte überlebt keinen Plattenausfall und keinen gelöschten VPS.
